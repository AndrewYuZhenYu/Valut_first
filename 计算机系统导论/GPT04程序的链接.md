# 第四章 程序的链接

> [!abstract] 本章知识主线
> **源程序 → 可重定位目标文件 → 符号解析 → 重定位 → 可执行文件 → 加载 → 运行。**
>
> 理解这条主线，需要掌握三个相互联系的问题：
> 1. **目标文件里有什么**：ELF 头、节、符号表、重定位表、程序头表。
> 2. **链接器做什么**：找到每个外部名字对应的定义，合并节并修正地址。
> 3. **程序怎样运行**：加载器将可装入段映射到虚拟地址空间；共享库还可能由动态链接器处理。

## 一、程序为什么需要链接

### 1. 从源代码到可执行文件

C 程序并不能以源代码形式直接被 CPU 执行。以 `hello.c` 为例：

```c
#include <stdio.h>

int main(void) {                          // 程序的入口函数
    printf("hello, world\n");           // 调用标准库函数输出文字
    return 0;                            // 正常结束程序
}
```

GCC 驱动的典型处理过程：

| 阶段 | 输入 | 输出 | 主要工作 |
| --- | --- | --- | --- |
| 预处理 | `hello.c` | `hello.i` | 展开头文件、宏和条件编译 |
| 编译 | `hello.i` | `hello.s` | 将预处理后的 C 程序翻译为汇编语言 |
| 汇编 | `hello.s` | `hello.o` | 生成机器指令与可重定位目标文件 |
| 链接 | `hello.o` 等 | `hello` | 解析符号、重定位、生成可执行文件 |

可用以下命令分别停在不同阶段（以 Linux/GCC 为例）：

```bash
gcc -E hello.c -o hello.i    # 只进行预处理
gcc -S hello.c -o hello.s    # 编译为汇编文件
gcc -c hello.c -o hello.o    # 生成可重定位目标文件
gcc hello.o -o hello         # 链接得到可执行文件
./hello                      # 运行程序
```

> [!important] 为什么汇编后还不能直接运行？
> `hello.o` 虽然含有机器指令，但它对 `printf` 等外部函数的引用尚未完成最终处理。链接器必须把引用关联到正确的定义，并为需要重定位的位置补上地址信息。

### 2. 链接器的由来：地址不能总靠程序员手动计算

机器语言时代，如果跳转目标位置变化，原先记录的跳转地址可能随之失效。汇编语言引入 `L0`、`P1` 等**符号（symbol）**：

- **符号定义（definition）**：某个函数、变量或标号实际在何处被定义。
- **符号引用（reference）**：其他指令或数据需要使用这个定义。
- **链接（linking）**：将来自不同目标模块的引用与定义对应起来，并对相关地址进行调整。

例如，一份文件定义函数 `add`，另一份文件调用它；编译器可以先单独编译两个文件，由链接器最后确定函数引用如何指向其实现。

### 3. 模块化带来的好处

**模块化**：将程序拆分为多个源文件，团队成员可以分别维护不同功能；常用函数还可以集中成函数库。

**编译效率**：仅修改一个源文件时，一般只需要重新编译该文件，再与其他已有目标文件链接，无需重新编译整个工程。

**复用效率**：程序可以引用公共函数库而不复制源代码。对于静态库，通常仅抽取所需的目标模块；对于共享库，多个进程还可以共享可共享的代码页。

### 4. 链接的两个核心任务

| 任务 | 回答的问题 | 典型操作 |
| --- | --- | --- |
| **符号解析（Symbol Resolution）** | `swap` 到底由哪个目标模块定义？ | 将 `main.o` 对 `swap` 的引用与 `swap.o` 中的定义关联 |
| **重定位（Relocation）** | `swap` 的地址确定后，机器指令如何引用它？ | 合并节、分配地址、修改待重定位字段 |

> [!tip] 记忆方式
> **符号解析负责“找人”，重定位负责“定地址、改引用”。** 两者有关联，但不是同一个操作。

## 二、贯穿全章的双文件示例

以下示例保持两个源文件独立编译，后文用它分析符号、节和重定位。

**`main.c`**

```c
int buf[2] = {1, 2};               // 定义已初始化的全局数组 buf
void swap(void);                  // 声明在别处定义的 swap 函数

int main(void) {                  // 定义全局函数 main
    swap();                       // 引用 swap 函数
    return 0;                     // 退出主程序
}
```

**`swap.c`**

```c
extern int buf[];                 // 声明外部数组：不在此处定义 buf
int *bufp0 = &buf[0];             // 定义全局指针，并引用外部数组 buf
static int *bufp1;                // 定义仅在本文件可见的静态指针

void swap(void) {                 // 定义可供其他文件调用的 swap 函数
    int temp;                     // 自动局部变量，通常使用栈等存储资源
    bufp1 = &buf[1];              // 让 bufp1 指向数组第二个元素
    temp = *bufp0;                // 暂存原来的第一个元素
    *bufp0 = *bufp1;              // 将第二个元素写到第一个位置
    *bufp1 = temp;                // 将原来的第一个元素写到第二个位置
}
```

```bash
gcc -c main.c -o main.o       # 单独编译 main.c
gcc -c swap.c -o swap.o       # 单独编译 swap.c
gcc main.o swap.o -o p        # 将两个目标文件链接为程序 p
./p                           # 程序会交换 buf 的两个元素，不产生终端输出
```

### 1. 从源码判断符号定义与引用

| 名称 | 定义位置 | 其他文件中的角色 | 链接器视角 |
| --- | --- | --- | --- |
| `buf` | `main.c` | `swap.c` 使用 `extern` 声明后引用 | 全局定义、外部引用 |
| `main` | `main.c` | — | 全局函数定义 |
| `swap` | `swap.c` | `main.c` 声明并调用 | 全局定义、外部引用 |
| `bufp0` | `swap.c` | 无跨文件引用 | 全局符号定义 |
| `bufp1` | `swap.c` | 仅 `swap.c` 使用 | **链接器局部符号** |
| `temp` | `swap` 的函数体 | 无 | 一般不是供链接器解析的普通目标符号 |

> [!warning] `static` 与“局部变量”不是一回事
> 在文件作用域定义 `static int *bufp1;`，会产生具有**内部链接属性**的静态存储期对象，通常在 `.bss` 中分配空间。函数内部的 `int temp;` 是自动局部变量，通常无须在目标文件符号表中成为一个可供跨模块解析的符号。调试信息中仍可能记录 `temp`，不要误以为“完全没有任何记录”。

### 2. 从结果理解为什么还要重定位

`main.o` 知道需要调用 `swap`，但并不知道最终程序中 `swap` 函数将被放到哪个虚拟地址；`swap.o` 知道使用了 `buf`，但也还不知道 `buf` 最终的存储地址。

因此，链接器既要找到定义，也要处理 **`call swap`** 和 **`&buf[0]`** 等地址引用。

## 三、目标文件与 ELF 基础

### 1. 目标代码、目标文件和文件格式

- **目标代码（Object Code）**：编译、汇编得到的机器语言代码。
- **目标文件（Object File）**：保存目标代码、数据以及相关元信息的文件。
- **ELF（Executable and Linkable Format）**：Linux 等类 UNIX 环境使用的一种可执行、可链接文件格式。

常见历史或平台相关格式有 DOS 的 COM、早期 UNIX 的 COFF、Windows 的 PE，以及 Linux 的 ELF。具体平台的编译产物不一定是 ELF；例如 macOS 常用 Mach-O。

### 2. 三类目标文件

| 类别 | Linux 常见形式 | 用途 | 最主要特点 |
| --- | --- | --- | --- |
| **可重定位目标文件** | `.o` | 参与进一步链接 | 地址和外部引用尚待链接处理，包含符号与重定位信息 |
| **可执行目标文件** | `a.out` 或自定义名称 | 被加载并执行 | 含程序入口与供加载器使用的程序头表 |
| **共享目标文件** | `.so` | 由其他程序动态链接 | 通常可在加载时或运行时加入进程地址空间 |

Windows 中常见的对应形式分别是 `.obj`、`.exe`、`.dll`。静态库 `.a` **不是第四类 ELF 目标文件**，而是把若干 `.o` 打包形成的归档文件。

> [!note] 为什么现代可执行程序有时显示 `Type: DYN`？
> 现代 Linux 发行版的 GCC 可能默认生成 **PIE（位置无关可执行文件）**。因此 `readelf -h app` 的文件类型可能是 `DYN`，而不是传统非 PIE 可执行文件的 `EXEC`。**程序能否作为入口执行**不能仅凭文件类型为 `DYN` 就否定；还要结合入口、程序头和动态链接信息判断。

> [!note] “地址从 0 开始”如何理解？
> 典型的 32 位 `.o` 示例通常用**节内偏移量**定位函数或数据，因此一个目标文件中 `.text` 和 `.data` 的相对偏移都可以各自从 0 开始；不意味着整个 `.o` 文件的物理字节从 0 开始都是代码，也不意味着多个节拥有相同的最终运行地址。

### 3. ELF 的两种视图：节与段

**链接视图**主要关注 **节（Section）**：让链接器知道哪些指令、变量、符号和重定位记录需要被处理。

**执行视图**主要关注 **段（Segment）**：让加载器知道应该把文件的哪些部分映射到虚拟地址空间，以及分别授予什么权限。

| 比较项 | 节 Section | 段 Segment |
| --- | --- | --- |
| 主要使用者 | 编译器、汇编器、链接器、分析工具 | 操作系统加载器、动态链接器 |
| 主要描述依据 | 内容及链接处理性质 | 运行时内存映射与访问权限 |
| 关键索引结构 | **节头表** Section Header Table | **程序头表** Program Header Table |
| 示例 | `.text`、`.data`、`.bss`、`.symtab` | `PT_LOAD` 的只读/可执行段、可读写段 |

典型联系：

```text
链接视图（节）                         执行视图（段）
.text ───────────────┐
.rodata ─────────────┼─────────→ 可读/可执行装入段
.init 等 ────────────┘
.data ───────────────┐
.bss ────────────────┴─────────→ 可读/可写装入段
.symtab、.debug ────────────────→ 一般不直接映射为运行所需的装入段
```

以上是**便于理解的典型布局**；真实文件可能有多个 `PT_LOAD` 段，`.rodata` 也可能单独处于只读段。具体关系应以程序头表为准。

### 4. 关键节的内容与作用

| 节名 | 典型内容 | 是否通常需要装入运行内存 |
| --- | --- | --- |
| `.text` | 编译后的机器指令 | 是，通常可执行 |
| `.rodata` | 字符串字面量、只读常量、某些跳转表 | 是，通常只读 |
| `.data` | 非零初始化的静态存储期对象等 | 是，通常可读写 |
| `.bss` | 不需要在文件中逐字节保存初值的零初始化/未初始化静态数据 | 运行时需要内存空间，但文件中通常不保存其全部内容 |
| `.symtab` | 符号表 | 通常不需要作为运行段装入 |
| `.strtab` | 符号名等字符串 | 通常不需要 |
| `.shstrtab` | **节名**字符串表 | 通常不需要 |
| `.rel.text` / `.rel.data` | 针对代码节/数据节的重定位记录 | 通常供静态链接处理 |
| `.debug_*` | 调试相关信息 | 通常不需要 |

> [!important] `.bss` 为什么节省磁盘空间？
> `.bss` 通常属于 ELF 的 `SHT_NOBITS` 类型。文件记录其**大小和属性**，但不为这部分零初始化存储逐字节存放数据；加载后依然要为它提供相应的内存。换句话说：**磁盘文件占用小，不等于运行时内存占用为零。**

**变量与节的关系示例**（具体位置受编译器、优化及链接脚本影响）：

```c
int x = 100;                       // 典型情况：.data（已初始化且非零）
int y;                             // 典型情况：.bss（零初始化）
static int a = 1;                  // 典型情况：.data，且只有文件内部可见
static int b;                      // 典型情况：.bss，且只有文件内部可见
const char *message = "hello";    // 指针自身可能在 .data，字符串通常在只读区域
```

变量的 `static` **决定链接属性和存储期**，不直接等于“必须放入 `.bss`”；最终节取决于初始化情况等因素。

**`.rodata` 的另一个常见来源：**编译器可能为较密集的 `switch` 分支生成跳转表。例如：

```c
int classify(int x) {               // 根据整数值选择返回结果
    switch (x) {                    // 多分支选择语句
        case 10: return 1;          // 输入为 10
        case 11: return 2;          // 输入为 11
        case 12: return 3;          // 输入为 12
        case 13: return 4;          // 输入为 13
        default: return 0;          // 其他输入返回 0
    }
}
```

编译器可能生成条件跳转、查表指令或其他等效机器码；**跳转表放入只读节是可能的实现方式，而不是每个 `switch` 都必然生成跳转表**。

### 5. ELF 头（ELF Header）

ELF 头位于文件开头，用来标识文件格式并记录定位其他结构的信息。重点字段如下：

| 字段 | 含义 |
| --- | --- |
| `e_ident` | 魔数、32/64 位类别、字节序等标识信息 |
| `e_type` | 文件类型，如 `REL`、`EXEC`、`DYN` |
| `e_machine` | 目标指令集架构，如 Intel 80386 |
| `e_entry` | 入口虚拟地址；可重定位文件中通常为 0 |
| `e_phoff` | 程序头表在文件中的偏移 |
| `e_shoff` | 节头表在文件中的偏移 |
| `e_phentsize` / `e_phnum` | 程序头表单个表项大小 / 表项数量 |
| `e_shentsize` / `e_shnum` | 节头表单个表项大小 / 表项数量 |
| `e_shstrndx` | 节名字符串表在节头表中的索引 |

ELF 的前四个魔数字节是 `7F 45 4C 46`，后面三个 ASCII 字符对应 `ELF`。在常见 ELF32 的例子里，ELF 头大小为 **52 字节**，但 ELF64 头大小和相关结构均不同。

```bash
readelf -h main.o              # 查看目标文件 ELF 头
readelf -h p                   # 查看可执行文件 ELF 头
```

### 6. 节头表（Section Header Table）

**节头表不是节内容本身**，而是描述各个节的目录。一个表项通常包含：

| 字段 | 含义 |
| --- | --- |
| `sh_name` | 节名称在 `.shstrtab` 内的偏移 |
| `sh_type` | 节类型，如 `PROGBITS`、`NOBITS`、`SYMTAB`、`STRTAB` |
| `sh_flags` | 节的属性标志 |
| `sh_addr` | 装入后对应的虚拟地址（若适用） |
| `sh_offset` | 节在文件中的偏移 |
| `sh_size` | 节的逻辑大小 |
| `sh_link` / `sh_info` | 与其他节关联时的辅助信息 |
| `sh_addralign` | 对齐要求 |
| `sh_entsize` | 当节由固定长度表项组成时，单个表项的大小 |

常见 `readelf -S` 标志：`W` 表示可写、`A` 表示运行时需要分配内存、`X` 表示可执行。比如 `.text` 常见 `AX`，`.data` 和 `.bss` 常见 `WA`，`.rodata` 常见 `A`。

```bash
readelf -S main.o              # 显示节头表（节类型、文件偏移、大小、属性）
readelf -SW main.o             # 宽格式显示，便于查看较长名称
objdump -h main.o              # 另一种查看节信息的方式
```

> [!warning] 文件偏移 ≠ 虚拟地址
> `sh_offset` 表示字节在磁盘文件中的位置；`sh_addr` 表示运行时对应地址（如有）。两者在含义上不同，不能因为数值接近而直接混用。

### 7. 一个可观察的 `readelf` 练习

建立简单目标文件：

```c
int initialized = 10;             // 已初始化全局数据
int uninitialized;                // 未初始化全局数据

int add(int a, int b) {            // 生成函数指令
    return a + b;                  // 返回两个参数之和
}
```

保存为 `sample.c`，执行：

```bash
gcc -O0 -c sample.c -o sample.o  # 生成可重定位目标文件
readelf -h sample.o               # 观察 Type、Machine 等字段
readelf -S sample.o               # 找到 .text、.data、.bss
readelf -s sample.o               # 查看定义符号及其节索引
```

先看 `.data` 与 `.bss`，再通过符号表中 `Ndx` 字段把变量与节联系起来。**节名、偏移、索引和优化后的具体布局，以本机实际输出为准。**

## 四、符号、符号表与符号解析

### 1. 三种链接器符号

每个可重定位模块通常都包含自己的符号表，用来描述模块定义或引用的符号。

| 类别 | 定义来源 | 可见范围 | 双文件示例 |
| --- | --- | --- | --- |
| **Global symbols（本模块定义的全局符号）** | 当前模块定义 | 其他模块可以引用 | `main.o` 中的 `buf`、`main`；`swap.o` 中的 `swap`、`bufp0` |
| **External symbols（外部定义的全局符号）** | 其他模块定义 | 当前模块需要引用 | `main.o` 对 `swap` 的引用；`swap.o` 对 `buf` 的引用 |
| **Local symbols（链接器局部符号）** | 当前模块定义 | 当前模块内部 | `swap.o` 中的 `bufp1` |

注意，“链接器局部符号”不等同于函数内部的自动局部变量；后者的名字一般不需要参与跨模块的符号解析。

### 2. 定义和声明、`extern` 和 `static`

**声明**主要告诉编译器符号的名称及类型；**定义**还承担创建实体（或实现函数）的作用。

```c
extern int count;                  // 声明：count 定义在其他地方
int total = 0;                    // 定义：创建全局变量 total
static int internal = 5;          // 定义：只允许本翻译单元通过此名字访问

int calculate(int x);             // 函数声明，没有提供实现
int calculate(int x) {            // 函数定义：提供实现
    return x * 2;                 // 计算并返回结果
}
```

容易混淆的形式：

```c
extern int n;                      // 只有声明；不会在这里建立 n 的定义
int n;                             // 文件作用域的暂定定义（tentative definition）
extern int m = 3;                  // 带初始化的变量定义，即使写了 extern
```

> [!warning] 在头文件里直接写 `int count;` 的风险
> 多个 `.c` 文件包含同一个头文件后，可能产生多个**暂定定义**。在现代 GCC 的默认 `-fno-common` 设置下，这往往引发 `multiple definition`。更可靠的方法是：**头文件写 `extern int count;`，恰好一个 `.c` 文件写 `int count = 0;`。**

### 3. ELF 符号表 `.symtab`

ELF 符号表是由许多表项组成的结构。学习时重点理解以下字段，不必机械背诵结构体定义。

| 字段（ELF32） | 记录内容 |
| --- | --- |
| `st_name` | 符号名在 `.strtab` 中的偏移 |
| `st_value` | 在 `.o` 中常表示节内偏移；可执行文件中可能表示虚拟地址 |
| `st_size` | 符号代表对象的字节数，如函数或数组的大小 |
| `st_info` | 符号**绑定属性**及**类型** |
| `st_shndx` | 符号属于哪个节，或表示特殊节索引 |

常见符号类型：`FUNC`（函数）、`OBJECT`（数据对象）、`SECTION`（节）、`FILE`（源文件信息）、`NOTYPE`（类型未明确）。

常见绑定属性：`GLOBAL`、`LOCAL`、`WEAK`。

`Ndx`（节索引）字段的常见特殊值：

- `UND`：本模块中**未定义**，等待其他模块或动态链接器解决。
- `ABS`：绝对符号，通常不随普通节地址改变而重新定位。
- `COM`：传统编译配置下的**公共符号**（common symbol），常用于尚未分配具体节的暂定定义。

以双文件示例为例，可以从 `readelf -s main.o` 中找到 `buf`、`main` 的定义，以及 `swap` 的 `UND` 条目；从 `readelf -s swap.o` 中找到 `buf` 的 `UND` 条目和 `swap` 的定义。

```bash
readelf -s main.o                # 显示 main.o 中的符号表
readelf -s swap.o                # 显示 swap.o 中的符号表
nm main.o                        # 用更紧凑的形式显示符号
nm swap.o                        # 对照查看 swap.o 的符号
```

`nm` 的常见字母：

| 字母 | 常见含义 |
| --- | --- |
| `T` / `t` | 代码节中的全局 / 局部符号 |
| `D` / `d` | 已初始化数据节中的全局 / 局部符号 |
| `B` / `b` | `.bss` 中的全局 / 局部符号 |
| `U` | 未定义、需要从其他地方解析的符号 |
| `C` | 公共符号（common） |
| `W` / `w` | 弱符号（具体语义还取决于是否已定义） |

这些字母是工具对常见情况的简化展示，不等于 ELF 所有类型的完整定义。

### 4. 符号解析到底怎样做

**符号解析（Symbol Resolution）**的目标是：把目标模块中的每一个需要解析的符号引用，关联到适当的定义。

仍以 `main.o` 和 `swap.o` 为例：

1. `main.o` 有 `main`、`buf` 的定义，也有对 `swap` 的未定义引用。
2. `swap.o` 有 `swap`、`bufp0`、`bufp1` 等定义，也有对 `buf` 的未定义引用。
3. 链接器将 `main.o` 中的 `swap` 引用与 `swap.o` 中的 `swap` 定义关联。
4. 将 `swap.o` 中的 `buf` 引用与 `main.o` 中的 `buf` 定义关联。
5. 解析完成后，才能依据合并后的布局修正需要重定位的地址字段。

> [!important] 解析不是“把函数内容复制到调用处”
> 解析建立的是**符号引用与定义的关系**。静态链接后，目标文件中的相关代码、数据和地址引用可能被合并并调整，但 `swap()` 并不因此变成在 `main()` 中原地展开的代码。函数内联是另一个概念。

### 5. 强符号和弱符号：规则与适用边界

课程中讨论的传统 C/GCC 场景，可以先按下列方式理解：

- 函数定义和**已初始化的全局变量定义**，属于强定义。
- 旧式 GCC 默认 `-fcommon` 环境下，**未初始化的全局变量暂定定义**常被处理为 common 符号，链接时可以与其他定义合并。

在这一传统教学模型中，多重定义的三个规则是：

1. **多个强定义：报重复定义错误。**
2. **一个强定义与若干 common 暂定定义：采用强定义。**
3. **若干 common 暂定定义：可合并为一个公共符号定义。**

> [!warning] 重要的版本差异：现代 GCC 并非默认采用上述第三条
> GCC 10 起默认 `-fno-common`。文件作用域的 `int x;` 通常直接放入 `.bss` 并作为普通全局定义，两个文件分别写 `int x;` 时可能立即发生多重定义错误。需要演示传统 common 规则，可显式使用 `-fcommon`。
>
> 另外，**`COMMON` 暂定定义和 ELF 真正的 `STB_WEAK` 弱绑定符号不是同一个概念**。传统入门教学常把它们放在“强/弱”规则下，但分析真实 ELF 文件时必须加以区分。

#### 例 1：两个强定义——链接失败

**`a.c`**

```c
int x = 10;                        // 第一个具有外部链接属性的全局定义
int get(void) {                    // 定义可被外部调用的函数 get
    return x;                      // 返回本模块看到的 x
}
```

**`b.c`**

```c
int x = 20;                        // 第二个同名强定义：与 a.c 冲突
int get(void);                     // 声明 get 函数

int main(void) {                   // 程序入口
    return get();                  // 调用另一个文件的函数
}
```

```bash
gcc a.c b.c -o conflict         # 通常报 multiple definition of 'x'
```

修复：只在一个文件中定义 `x`，其他文件使用 `extern int x;`。

#### 例 2：观察 `-fcommon` 的影响

**`a.c`**

```c
int number;                        // 暂定定义
int get(void) {                    // 定义 get 函数
    return number;                 // 读取 number
}
```

**`b.c`**

```c
int number;                        // 另一个同名暂定定义
int get(void);                     // 声明外部函数

int main(void) {                   // 定义入口函数
    number = 7;                    // 给合并后的变量赋值
    return get();                  // 返回同一个变量的值
}
```

```bash
gcc a.c b.c -o example            # 现代 GCC 默认可能报告重复定义
gcc -fcommon a.c b.c -o example   # 演示传统 common 符号合并规则
./example                         # 返回码通常为 7；不一定有可见输出
```

此例用于**理解旧式规则**，而不是推荐在工程中继续依赖多个暂定定义。

#### 例 3：不同类型的同名变量为何更危险

一个典型的历史案例：一个模块把 `d` 视为 `int`，另一个模块把 `d` 视为 `double`，且二者意外共享同名存储位置。在特定 32 位、小端、旧式 common 链接布局下：

- `double` 的 `1.0` 对应 64 位位模式 `0x3FF0000000000000`。
- 按小端序写入内存时，低地址的四字节为 `00 00 00 00`，高地址的四字节为 `00 00 F0 3F`。
- 如果错误地把后四字节解释为 32 位 `int`，得到 `0x3FF00000 = 1072693248`。

因此，这类示例可能表现为 `d=0, x=1072693248`，说明类型不匹配与内存覆盖会造成难以定位的错误。**这是依赖特定平台、编译器和错误声明的现象，不是符合规范程序应当保证的输出。**

### 6. 避免多重定义问题的实际规范

- 能不用跨文件全局变量，就优先使用函数参数、返回值或模块接口。
- 仅供本文件使用的变量与函数，适当使用文件作用域 `static`。
- 头文件中为公共变量写 `extern` 声明；只在一个源文件中提供定义。
- 使用一致的函数原型与变量类型；多个文件应包含同一个正确的头文件，减少声明不一致的风险。

**正确的头文件分离示例：**

**`counter.h`**

```c
#ifndef COUNTER_H
#define COUNTER_H

extern int counter;                // 只声明共享变量，不在头文件中定义
void increment(void);             // 只声明公共函数接口

#endif
```

**`counter.c`**

```c
#include "counter.h"             // 使用统一的接口声明

int counter = 0;                   // 唯一的变量定义

void increment(void) {            // 函数实现
    ++counter;                    // 将共享计数加 1
}
```

**`main.c`**

```c
#include "counter.h"             // 引入相同的声明，保证类型一致

int main(void) {                   // 程序入口
    increment();                   // 调用另外一个目标模块中的函数
    return counter;                // 返回当前计数值，结果为 1
}
```

```bash
gcc -c counter.c main.c          # 分别得到 counter.o 和 main.o
gcc counter.o main.o -o counter   # 链接两个目标文件
```

## 五、静态库及其链接顺序

### 1. 静态库是什么

**静态库（Static Library）**通常是多个可重定位目标文件 `.o` 的归档集合，Linux/GNU 环境常以 `.a` 为扩展名。

```text
myproc1.c ──编译──→ myproc1.o ─┐
                               ├──归档──→ libmine.a
myproc2.c ──编译──→ myproc2.o ─┘
```

使用静态库时，链接器通常**按需抽取**能满足未解析引用的库成员 `.o`，而不是毫无选择地复制整个库。

> [!note] 静态库与普通目标文件的区别
> 单独把 `myproc1.o myproc2.o` 放在链接命令行中，链接器直接处理这两个目标文件；写成 `libmine.a` 后，通常先从归档中**选择需要的成员**。这正是静态库能简化工程依赖管理的重要原因。

### 2. 创建自己的静态库

**`myproc1.c`**

```c
#include <stdio.h>

void myfunc1(void) {               // 提供公共函数 myfunc1
    puts("This is myfunc1!");     // 调用标准 I/O 库函数
}
```

**`myproc2.c`**

```c
#include <stdio.h>

void myfunc2(void) {               // 提供另一个公共函数 myfunc2
    puts("This is myfunc2!");     // 该函数与 myfunc1 独立
}
```

**`main.c`**

```c
void myfunc1(void);                // 声明库中提供的 myfunc1

int main(void) {                   // 定义程序入口
    myfunc1();                     // 使用 myfunc1，但并未调用 myfunc2
    return 0;                      // 正常返回
}
```

执行步骤：

```bash
gcc -c myproc1.c myproc2.c main.c    # 得到三个 .o 文件
ar rcs libmine.a myproc1.o myproc2.o  # 归档形成静态库
ar -t libmine.a                       # 列出库中包含的成员
nm libmine.a                          # 查看静态库提供或引用的符号
gcc main.o ./libmine.a -o myproc      # 在目标文件之后给出静态库
./myproc                              # 输出 This is myfunc1!
```

在这个例子里，链接器需要 `myfunc1`，通常会抽取 `myproc1.o`；没有被其他代码引用的 `myfunc2` 不会仅因存在于归档中就要求抽取整个 `myproc2.o`。

### 3. 用 `E`、`U`、`D` 理解静态库查找

传统教学模型用三个集合概括扫描过程：

| 集合 | 含义 |
| --- | --- |
| `E` | 最终选中并参与链接的目标模块集合 |
| `U` | 当前尚未解析的符号引用集合 |
| `D` | 当前已找到的定义符号集合 |

以上面的 `main.o` 和 `libmine.a` 为例：

1. 处理 `main.o`：它定义 `main`，同时引用 `myfunc1`，因此需要解析 `myfunc1`。
2. 扫描 `libmine.a`：找到定义 `myfunc1` 的成员 `myproc1.o`，将该成员加入选中模块集合。
3. 因为 `myproc1.o` 调用了 `puts`，还会产生对 C 标准库函数的需求。
4. GCC 驱动随后会按链接配置提供相关运行库：如果选择静态链接，会继续抽取所需库成员；如果默认动态链接，对标准库的引用则可能留给动态链接机制处理。
5. `myproc2.o` 不包含当前需要的符号，通常不会被抽取。

> [!important] `E/U/D` 是理解静态链接的教学模型
> 链接器实际还有弱引用、节垃圾回收、符号版本、链接脚本等机制；`E/U/D` 足以解释“按需抽取成员”和“库顺序为什么重要”，但不是所有链接器行为的完整算法规范。

### 4. 静态库顺序为何影响链接结果

对传统 GNU 静态库处理方式，链接器**从左到右**扫描输入。归档中的成员通常只在当前需要某个符号定义时才被抽取。

```bash
gcc main.o ./libmine.a -o app      # 通常正确：先看到 myfunc1 的未定义引用
gcc ./libmine.a main.o -o app      # 通常错误：扫描库时尚不知道要用 myfunc1
```

第二行在扫描到 `libmine.a` 时，未解析集合中还没有 `myfunc1`，因此不会抽取 `myproc1.o`；之后扫描 `main.o` 才发现这一需要，归档已经处理过了，于是可能出现 `undefined reference to 'myfunc1'`。

如果库命名为 `libmine.a`，可采用简写：

```bash
gcc main.o -L. -lmine -o app      # -L. 在当前目录查找库；-lmine 查找 libmine
```

> [!warning] `-lmine` 不一定强制使用静态库
> 如果同一搜索位置同时存在 `libmine.so` 和 `libmine.a`，GCC/链接器通常优先选择共享库（受平台与选项影响）。若目的是专门演示静态库成员抽取，可以明确写 `./libmine.a`。

### 5. 多个库的依赖和循环依赖

若 `func.o` 依赖 `libx.a`，而 `libx.a` 又依赖 `libz.a`，通常应将提供依赖的库写在后面：

```bash
gcc func.o libx.a libz.a -o app       # libx 先被使用，libz 负责满足后续引用
```

存在循环依赖时，简单的单次扫描可能失败。传统方法可以在命令行中重复提供某个归档：

```bash
gcc func.o libx.a liby.a libx.a -o app   # 再扫一次 libx 以解决回头出现的引用
```

GNU 链接器还提供库组方式（适用于确有必要时）：

```bash
gcc func.o -Wl,--start-group libx.a liby.a -Wl,--end-group -o app
# 链接器重复扫描组内静态库，以解决相互依赖的符号
```

`--start-group` 可能增加链接开销，正常项目更应优先调整合理的模块依赖关系。

## 六、重定位：把符号引用变成正确的地址

### 1. 重定位的三个步骤

符号解析确定“引用对应谁”之后，链接器才能结合地址布局继续处理：

1. **合并和布局相关节**：把已选中目标模块中性质相同或兼容的输入节安排到输出节中，考虑对齐和链接脚本规则。
2. **重定位定义符号**：确定输出节的地址，进而得到各个函数、全局变量等符号的最终地址。
3. **重定位引用符号**：读取重定位表，对代码或数据中需要修改的地址字段写入计算结果。

> [!important] 为什么“找到函数”仍然不够？
> `swap` 在 `swap.o` 中可能位于 `.text` 节的偏移 0；但链接器把 `main.o` 的代码安排在前面后，`swap` 不再位于输出 `.text` 的开头。调用指令必须根据新的布局计算目标地址或相对位移。

### 2. 重定位表项：哪里改、为谁改、怎么改

在这里研究的 ELF32/i386 体系中，常见结构叫 `Elf32_Rel`，可把它理解为：

- **`r_offset`**：需要修改的字段位于其所在节的哪个偏移处。
- **`r_info`**：同时编码引用的符号表索引 `r_sym` 和重定位类型 `r_type`。
- **加数（addend）**：`REL` 格式通常把加数预先存放在待修改的位置中。

```bash
readelf -r main.o                 # 查看 main.o 中的重定位记录
readelf -r swap.o                 # 查看 swap.o 中的重定位记录
objdump -dr main.o               # 同时显示反汇编和与指令相关的重定位项
objdump -s -j .data swap.o        # 观察原始 .data 字节（若此节存在）
```

`.rel.text`（不同工具可能显示为 `.rel.text` 等命名）保存针对代码节的重定位记录，`.rel.data` 保存针对数据节的记录。现代 x86-64 ELF 常见的是 **`.rela.text`、`.rela.data`** 等 `RELA` 形式，其加数由重定位表项显式提供。

> [!note] 不要把 `.rel.*` 与 `.rela.*` 混为一谈
> `REL` 与 `RELA` 的关键区别是**加数存放在哪里**，不是“前者表示静态链接、后者表示动态链接”。本节随后使用的是 32 位 i386 的 `REL` 计算方法。

### 3. IA-32 两种基本重定位类型

设：

- `S`：被引用的符号最终地址。
- `A`：加数（addend）。
- `P`：待重定位地址字段自身的地址。

则两种类型的经典计算式为：

| 类型 | 计算公式 | 使用场景 |
| --- | --- | --- |
| `R_386_32` | $S+A$ | 把绝对地址写到某字段中 |
| `R_386_PC32` | $S+A-P$ | 将相对于当前位置的偏移写入指令字段 |

这里写入的结果都是相应重定位字段的值，不是说 CPU 的所有访问方式都只使用这两种表达式。具体编码还要遵守处理器指令格式。

### 4. 典型计算一：`R_386_PC32` 的函数调用

考虑主函数调用 `swap` 的 IA-32 汇编代码：

```asm
call swap                       # 机器码 E8 后跟一个 32 位相对位移
```

设定以下关键地址条件：

- `main` 首地址是 `0x08048380`，代码长度为 `0x12` 字节。
- `swap` 紧随 `main`，并按 **4 字节边界**对齐。
- `call` 指令位于 `main` 的偏移 `0x6`，机器码第一个字节是 `E8`。
- 随后的四字节位移字段位于 `main` 偏移 `0x7`，初始内容是 `FC FF FF FF`，代表 `A=-4`。

**第一步：计算 `swap` 的最终地址。**

$$
0x08048380+0x12=0x08048392
$$

按 4 字节对齐，向上调整到：

$$
S=\operatorname{ADDR}(swap)=0x08048394
$$

**第二步：找到需要修改的字段所在位置。**

$$
P=0x08048380+0x7=0x08048387
$$

**第三步：套用 PC 相对重定位公式。**

$$
\begin{aligned}
V&=S+A-P\\
 &=0x08048394+(-4)-0x08048387\\
 &=0x9
\end{aligned}
$$

因此重定位后的 `call` 指令字节是：

```text
E8 09 00 00 00
```

这里 `09 00 00 00` 是小端序的 32 位数 `0x00000009`。

**第四步：验证 CPU 实际如何跳转。**

`call` 指令长 5 字节，执行时相对位移以**下一条指令的地址**为基准：

$$
0x08048386+5+9=0x08048394
$$

正好跳转到 `swap`。

> [!warning] 最容易错的地方：`P` 不是下一条指令地址
> 在公式 $S+A-P$ 中，`P` 是**位移字段开始位置** `0x08048387`，而不是 `call` 开始位置 `0x08048386`，也不是下一条指令地址 `0x0804838B`。正因为字段中预先有 `A=-4`，计算结果才恰好等于以“下一条指令”为起点的相对偏移 `9`。计算时应明确自己使用的是**重定位公式**还是**CPU 执行时的相对跳转公式**。

### 5. 典型计算二：`R_386_32` 的指针初始化

考虑 `swap.c` 中的定义：

```c
extern int buf[];                  // buf 实际定义在另一个目标模块
int *bufp0 = &buf[0];              // 全局指针的初值依赖 buf 的最终地址
```

按照给定的 32 位布局，假设：

- `buf` 最终地址是 `0x08049620`，数组含两个 `int`，共 8 字节。
- `bufp0` 被安排在 `buf` 后面，所以自己的地址为 `0x08049628`。
- 初始化表达式 `&buf[0]` 的加数 `A=0`。

因为 `R_386_32` 直接使用绝对值：

$$
V=S+A=0x08049620+0=0x08049620
$$

于是：

| 内容 | 地址或值 | 含义 |
| --- | --- | --- |
| `buf` 的地址 | `0x08049620` | 数组起始位置 |
| `bufp0` 的地址 | `0x08049628` | 指针变量本身存放在哪里 |
| `bufp0` 保存的值 | `0x08049620` | 指针指向 `buf[0]` |
| 文件中的初始化字节 | `20 96 04 08` | 地址值按小端序存储 |

> [!important] **指针变量的地址**与**指针保存的地址**
> `&bufp0` 是 `0x08049628`；`bufp0` 的值是 `0x08049620`。一个表示**指针对象自己的位置**，另一个表示**它指向哪里**，是不同概念。

如果初始化的是 `&buf[1]`，且 `sizeof(int)=4`，则加数 `A=4`：

$$
0x08049620+4=0x08049624
$$

对应的小端字节为 `24 96 04 08`。

### 6. `swap.o` 中的六处重定位

在下面采用的**特定 IA-32、非 PIC 编译结果**中，`swap.o` 的 `.text` 共有六处需要重定位。取以下最终布局：

- `buf = 0x08049620`
- `bufp0 = 0x08049628`
- `bufp1 = 0x08049700`
- `buf[1] = 0x08049624`

| `.text` 中的偏移 | 引用对象 | 填入地址 | 小端序字段 |
| --- | --- | --- | --- |
| `0x08` | `bufp1` 本身 | `0x08049700` | `00 97 04 08` |
| `0x0C` | `&buf[1]` | `0x08049624` | `24 96 04 08` |
| `0x11` | `bufp0` 本身 | `0x08049628` | `28 96 04 08` |
| `0x1B` | `bufp0` 本身 | `0x08049628` | `28 96 04 08` |
| `0x21` | `bufp1` 本身 | `0x08049700` | `00 97 04 08` |
| `0x2A` | `bufp1` 本身 | `0x08049700` | `00 97 04 08` |

这些偏移是**具体示例中的指令编码位置**，不是 C 语句固定拥有的偏移。改变优化级别、架构、编译器版本、PIC 设置都会改变指令及重定位记录。

### 7. 为什么局部符号也要重定位

`bufp1` 的名字只在 `swap.o` 中有效，因此不需要跨模块寻找其定义；但它在 `.bss` 中的**最终地址仍然要随节的输出布局而确定**。因此局部符号一样可能被重定位。

**是否需要跨模块解析**与**是否需要修正地址**是两个独立问题。

### 8. 重定位常见错误

- 把重定位类型误当作“绝对地址/相对地址”两个完全独立的地址空间。
- 忘记加数 `A`，导致 PC 相对位移算错 4 字节。
- 忽略小端序，把 `20 96 04 08` 当成地址 `0x20960408`。
- 把节内偏移当成最终虚拟地址，漏掉输出节起始地址。
- 忽略对齐填充：例如 `main` 后面可能有 `nop`，`swap` 不一定紧贴上一条指令。
- 用现代 64 位反汇编结果逐字节对照旧版 IA-32 汇编示例：指令编码和重定位类型可能完全不同。

## 七、可执行文件、程序头表与程序加载

### 1. 可执行文件与 `.o` 的关键区别

链接完成后，在典型静态链接的可执行 ELF 中：

- 入口地址等信息已设置。
- 各个定义符号已经按输出布局得到地址。
- 静态链接阶段可以确定的重定位项已经被处理。
- 程序头表提供**文件内容到虚拟内存段的映射信息**。

动态链接的可执行文件则还可能包含由动态链接器在加载或运行时处理的重定位信息。因此，不应笼统地认为“只要是可执行文件，就绝对没有任何剩余重定位”。

### 2. 程序头表（Program Header Table）

节头表告诉链接器“文件中每个节是什么”；**程序头表**主要告诉加载器“运行时该把哪些范围映射到什么位置”。

一个 ELF32 程序头表项的典型字段：

| 字段 | 作用 |
| --- | --- |
| `p_type` | 段类型；常见 `LOAD`，特殊类型包括 `INTERP` 等 |
| `p_offset` | 段在文件中的起始偏移 |
| `p_vaddr` | 段映射到的虚拟地址 |
| `p_filesz` | 文件中该段实际初始化内容的字节数 |
| `p_memsz` | 该段在内存中应占的字节数 |
| `p_flags` | 段权限，如读 `R`、写 `W`、执行 `E` |
| `p_align` | 对齐要求 |

```bash
readelf -l p                     # 读取程序头表及节到段的映射关系
objdump -p p                     # 查看程序头及动态链接相关信息
```

### 3. 为什么 `p_memsz` 可以大于 `p_filesz`

典型情况是 `.data` 和 `.bss` 属于同一个可装入数据段。文件中有已初始化的数据字节，内存中还需要额外的零填充区域。

一个示例：

| 属性 | 示例值 | 解释 |
| --- | --- | --- |
| `p_offset` | `0x00000F0C` | 数据段在文件中开始的位置 |
| `p_vaddr` | `0x08049F0C` | 数据段在虚拟空间中的开始位置 |
| `p_filesz` | `0x108` | 文件包含 264 字节待初始化内容 |
| `p_memsz` | `0x110` | 内存总共保留 272 字节 |
| 额外的零填充空间 | `0x110 - 0x108 = 0x8` | 8 字节不需要由磁盘逐字节提供 |

> [!important] 必须掌握的关系
> 对常见需要零填充的 `PT_LOAD` 段，`p_memsz` 大于 `p_filesz` 的部分在内存中按规定初始化为零，常用于承载 `.bss` 等内容。不能把这部分误算为磁盘上另有一块同等长度的数据节。

另外，装入段的文件偏移与虚拟地址往往需要满足相对于对齐值的同余关系；不能随意为每个段设置互不相干的起始地址。

### 4. 进程虚拟地址空间的典型布局

从低地址到高地址，一个传统 **32 位 Linux 进程**可粗略理解为：

```text
高地址（传统 IA-32 示例：用户区上界附近为 0xC0000000）
┌────────────────────────────────────────┐
│ 内核地址空间（用户态不可直接访问）      │
├────────────────────────────────────────┤
│ 用户栈（stack）：栈帧、局部变量等       │
│                ↓                       │
│ 共享库、内存映射区域（mmap）            │
│                                        │
│                ↑                       │
│ 堆（heap）：动态分配区域                │
│ 可读写数据段：.data、.bss 等            │
│ 代码/只读区域：.text、.rodata 等         │
├────────────────────────────────────────┤
│ 未映射或受保护的低地址空间              │
└────────────────────────────────────────┘
低地址
```

这是**用于理解的旧式 IA-32 典型图**。具体分界、栈与库的位置、PIE 和 ASLR（地址空间布局随机化）影响，都可能改变真实地址布局；不能把 `0x08048000` 或 `0xC0000000` 当成所有现代系统的固定规则。

### 5. 可执行文件如何被加载

以传统类 UNIX 环境为背景：

1. 用户请求运行程序，例如 `./p`。
2. Shell 通常通过创建子进程并执行程序映像替换等步骤启动它；`fork()` 与 `execve()` 是理解这个过程的重要系统调用。
3. 加载机制读取 ELF 头和程序头表，建立必要的虚拟内存映射。
4. 若程序需要动态链接，系统按解释器段信息启动动态链接器，处理共享库依赖和相关重定位。
5. 最终从 ELF 的程序入口点开始执行启动代码，再由运行时启动逻辑调用 `main`。

> [!warning] 入口地址通常不是 `main`
> ELF 头的 `e_entry` 一般指向运行时启动入口，例如 `_start`。启动代码负责准备 C 运行环境并调用 `main`；`main` 返回后仍有相应退出清理过程。因此“CPU 直接从 `main` 的第一条指令开始执行”并不准确。

### 6. 为什么加载不等于立刻把整个文件复制进内存

现代操作系统通常利用**虚拟内存映射与按需分页**加载可执行文件：

- 先建立虚拟地址与文件内容等后备存储之间的关系。
- 实际物理内存页可能在发生缺页时才装入。
- 需要零初始化的部分可使用零填充或按需分配机制。
- 同一个共享库的只读代码页可以在多个进程间共享物理内存。

因此，**文件存在磁盘上、虚拟地址可访问、物理页已实际驻留**是三个不同层次的状态。

## 八、动态链接与共享库

### 1. 静态库的局限性

静态链接可以生成更独立的可执行程序，但在大量程序反复使用相同函数库时，容易遇到：

- **磁盘空间占用**：相同的库目标代码可能被复制进许多可执行文件。
- **更新不灵活**：静态链接后的程序通常需要重新链接才能获得新版本库代码。
- **运行时共享受限**：不同静态链接程序各自携带库代码，通常不能像链接同一共享库那样自然共享同一份文件后备的代码页。

**共享库（Shared Library）**允许代码和数据作为单独模块提供，程序在加载时或运行过程中使用它。Linux 常见扩展名是 `.so`，Windows 常见形式是 `.dll`。

> [!note] 共享不等于“所有内容只有唯一一份物理副本”
> 多进程可以共享同一个共享库的只读代码页，但可写的全局数据通常要按进程维持各自的状态；写时复制、重定位、版本和装载方式都会影响实际内存占用。不要把共享库理解成“所有进程使用同一份可写全局变量”。

### 2. 静态链接与动态链接比较

| 维度 | 静态链接 | 动态链接 |
| --- | --- | --- |
| 库代码何时并入目标 | 链接时抽取库成员并集成 | 代码通常保留在独立共享库中 |
| 程序运行依赖 | 静态集成的代码通常不再需要原 `.a` | 运行时需要找到兼容的 `.so` |
| 库升级 | 一般需要重新链接程序 | 可在 ABI 兼容前提下更新共享库 |
| 共享代码页 | 不同程序的独立静态副本较难共享 | 适合多个进程共享代码页 |
| 链接时解析 | 需要处理静态目标符号引用和相关重定位 | 一些动态符号和重定位可留待加载/运行阶段处理 |

**注意**：一个程序可以同时使用某些静态库和某些共享库，二者不是非此即彼。

### 3. 加载时动态链接（Load-time Linking）

程序启动时，系统装载可执行映像；如果它依赖动态库，动态链接器需要定位并装入依赖、处理必要重定位、完成初始化等工作，然后把控制权交给程序入口。

典型 Linux ELF 可执行文件中可见 `INTERP` 程序头，它指向动态链接器的路径；例如不同架构上可能使用不同名称的 `ld-linux` 变体。不要把某个具体路径固定为所有机器通用。

```bash
readelf -l app                   # 查看是否存在 INTERP 段
readelf -d app                   # 查看动态段及 NEEDED 等依赖记录
ldd ./app                        # 在可信程序上查看动态库解析情况
```

> [!warning] `ldd` 主要用于可信程序
> `ldd` 在某些环境或实现中可能涉及执行被检查程序的加载路径。分析来源不明的二进制文件时，优先使用 `readelf -d` 等静态检查手段。

### 4. 动手创建可供启动时链接的共享库

**`myproc1.c`**

```c
#include <stdio.h>

void myfunc1(void) {               // 向共享库导出函数 myfunc1
    puts("This is myfunc1!");     // 使用标准库打印一行文本
}
```

**`myproc2.c`**

```c
#include <stdio.h>

void myfunc2(void) {               // 向共享库导出另一个函数
    puts("This is myfunc2!");     // 演示共享库可以包含多个源文件
}
```

**`main.c`**

```c
void myfunc1(void);                // 声明共享库中定义的函数

int main(void) {                   // 程序入口
    myfunc1();                     // 调用共享库函数
    return 0;                      // 正常退出
}
```

**编译并链接：**

```bash
gcc -fPIC -c myproc1.c myproc2.c                      # 先生成位置无关的目标代码
gcc -shared -o libmine.so myproc1.o myproc2.o          # 生成 ELF 共享对象
gcc main.c -L. -lmine -Wl,-rpath,'$ORIGIN' -o app     # 链接共享库，并设置相对运行时搜索路径
./app                                                 # 输出 This is myfunc1!
```

参数说明：

- `-fPIC`：生成**位置无关代码**，适合构建共享库。
- `-shared`：生成共享对象而不是普通可执行程序。
- `-L.`：将当前目录加入链接阶段的库搜索路径。
- `-lmine`：在 Linux/GNU 环境中查找 `libmine.so` 或 `libmine.a` 等合适文件。
- `-Wl,-rpath,'$ORIGIN'`：把 `$ORIGIN` 原样传给链接器，作为运行时查找库的位置；在 ELF 环境中通常表示**可执行文件所在目录**。其中单引号用于防止 Shell 提前展开变量。

> [!tip] 分清两个“找库”的阶段
> `-L.` 主要解决**构建时在哪里寻找库文件**；运行时能否找到 `libmine.so` 则由动态加载器的搜索规则决定。只写 `-L.`，不代表运行时一定能找到这个 `.so`。

### 5. 运行时动态链接（Run-time Linking）

**运行时动态链接**允许程序已经运行以后再按需装入某个共享库。典型 POSIX 接口在 `<dlfcn.h>` 中：

| 接口 | 作用 |
| --- | --- |
| `dlopen` | 打开并装入一个共享对象，获得句柄 |
| `dlsym` | 按符号名称查找地址 |
| `dlerror` | 获取动态链接器错误信息，同时清除已报告的错误状态 |
| `dlclose` | 关闭句柄并减少相应引用计数；不保证立即卸载所有映射 |

以下示例可以使用上节生成的 `libmine.so`；这里**不需要**在构建可执行文件时直接把它写进库依赖列表。

**`dynamic_main.c`**

```c
#include <stdio.h>
#include <dlfcn.h>

int main(void) {
    void *handle = dlopen("./libmine.so", RTLD_NOW);  // 运行时打开共享库并立即解析所需符号
    if (handle == NULL) {                           // 判断动态库是否装入失败
        fprintf(stderr, "%s\n", dlerror());        // 输出动态链接器的错误原因
        return 1;                                   // 失败时退出
    }

    dlerror();                                      // 清除先前可能遗留的错误状态
    void (*func)(void) = (void (*)(void))dlsym(handle, "myfunc1");
                                                   // 查找符号并转换为相应函数指针（POSIX 用法）
    const char *error = dlerror();                  // 检查本次符号查找是否出错
    if (error != NULL) {                           // 函数名称不存在等情况
        fprintf(stderr, "%s\n", error);            // 报告查找失败原因
        dlclose(handle);                            // 释放已取得的库句柄
        return 1;                                   // 退出程序
    }

    func();                                         // 经函数指针调用共享库中的 myfunc1

    if (dlclose(handle) != 0) {                     // 关闭库句柄并检查结果
        fprintf(stderr, "%s\n", dlerror());        // 输出关闭失败原因
        return 1;                                   // 退出程序
    }
    return 0;                                       // 执行成功
}
```

```bash
gcc dynamic_main.c -o dynamic_app -ldl   # 编译运行时动态装载程序
./dynamic_app                            # 从当前目录的 libmine.so 查找并调用 myfunc1
```

`-ldl` 在某些现代 glibc 环境下不再是必需的单独库选项，但保留它有助于兼容部分传统 Linux 开发环境。

**整体执行顺序：** `dlopen` → 检查句柄 → `dlsym` → 检查错误 → 调用函数指针 → `dlclose`。

> [!warning] `dlsym` 返回值应按平台规定使用
> POSIX 环境允许对函数符号进行相应函数指针转换；纯 ISO C 不保证所有对象指针与函数指针可以任意互转。本例限定在提供 `dlopen`/`dlsym` 的 POSIX 系统上，不应直接照搬到任意 C 平台。

## 九、位置无关代码（PIC）、GOT 与 PLT

### 1. 为什么共享库要支持位置无关

**位置无关代码（Position-Independent Code，PIC）**的核心目标，是让共享库的机器指令不依赖某一个固定装载基址，尽可能避免动态装载时修改代码段本身。

例如，某个函数在共享库内部位于相对偏移 `0x100`：

- 库被映射到基址 `0x50000000`，函数位于 `0x50000100`。
- 库被映射到基址 `0x70000000`，函数位于 `0x70000100`。

函数的**绝对地址改变**，但它与库内其他指令之间的**相对距离**可以保持不变。因此，PIC 可以优先使用相对寻址；对于地址无法在静态编译时确定的外部对象，通过间接表来处理。

> [!important] `-fPIC` 的作用
> `-fPIC` 让编译器生成适合共享对象的可重定位、位置无关代码。它不表示“共享库完全无需任何重定位”，而是使必须修改的位置更多集中在**数据区域中的地址表**等位置，减少或避免修改可共享的只读代码页。

### 2. 四类符号访问问题

PIC 的理解可以分为四种情形：

| 场景 | 典型处理思路 | 关键原因 |
| --- | --- | --- |
| ① **模块内函数调用、跳转** | 采用 PC 相对寻址 | 同一模块内两条指令的相对距离通常不变 |
| ② **模块内数据访问** | 用相对基址计算静态数据地址；某些情况下可直接用 RIP 相对寻址 | 代码与本地数据的相对位置可以确定 |
| ③ **模块外数据引用** | 通过 GOT 找到外部变量的实际地址 | 外部数据的位置无法在编译当前模块时确定 |
| ④ **模块间函数调用、跳转** | 通过 GOT / PLT 等机制进行间接调用，支持延迟绑定 | 外部函数位置通常需要动态链接器参与解析 |

这些是**教学分类**；真实编译器还会依符号可见性、架构、编译选项等选择更具体的策略。

### 3. 情形①：模块内部的函数调用

假设两个函数位于同一模块：

```c
static void bar(void) {            // 内部函数：不会作为对外导出的普通接口
    // 此处可以执行本模块内部的工作
}

void foo(void) {                   // 定义对外可见的 foo
    bar();                         // 调用同一模块内部的 bar
}
```

在典型 IA-32 相对跳转机制中，`call` 保存的可以是到目标函数的**相对位移**：

$$
\text{相对位移}=\text{目标地址}-\text{下一条指令地址}
$$

整个模块平移装载时，目标与来源同时增加相同基址，二者相减后不变。

### 4. 情形②：模块内部的数据访问

例如模块内的静态变量：

```c
static int a;                      // 定义模块内部静态存储期变量

void set_a(void) {                 // 定义内部数据操作函数
    a = 1;                        // 引用当前模块的静态数据
}
```

`.text` 中的相关指令和 `.data` / `.bss` 中的相关数据，可以依据模块内部固定的偏移关系确定访问位置。

在旧式 IA-32 PIC 中，常见一种方法是借助取 PC 的指令序列，建立一个模块相对基址，再加上数据偏移；**x86-64 通常有更直接的 RIP 相对寻址方式**，不必机械套用 IA-32 中通过函数调用获取 PC 的完整序列。

### 5. 情形③：模块外的数据引用——GOT

**GOT（Global Offset Table，全局偏移表）**是一组可供间接访问的地址表项。在某些典型动态重定位方案中，动态链接器将外部符号的地址写入 GOT，代码随后通过 GOT 表项访问目标。

```c
extern int external_value;         // 外部变量定义在其他目标模块中

int get_external(void) {           // 提供读取函数
    return external_value;         // 编译器可能通过 GOT 间接定位该变量
}
```

可以把机制简化成：

```text
当前共享库的代码
       │
       │ 使用相对于本模块的已知位置
       ▼
GOT 中 external_value 对应的地址表项
       │
       │ 动态链接器填入真实地址
       ▼
其他模块中的 external_value
```

这个关系是一张**地址查询表**，并不是把外部变量的值复制到 GOT。典型 GOT 数据项存放的是**指向变量的地址**。

### 6. 情形④：模块间函数调用——PLT

模块外函数和模块外数据都需要找到最终地址，但函数调用往往希望避免每次执行较长的地址获取序列，因此使用 **PLT（Procedure Linkage Table，过程链接表）**等机制。

概念关系：

```text
程序调用外部函数 ext()
        │
        ▼
跳到 ext 对应的 PLT 入口
        │
        ├─ 已解析：通过相关 GOT 表项跳到 ext 的实际地址
        │
        └─ 未解析：进入动态链接器的解析路径
                         │
                         ▼
                 找到 ext 的地址
                         │
                         ▼
                更新相关表项后调用 ext
```

#### 延迟绑定（Lazy Binding）

**延迟绑定**是指：对于部分可以推迟处理的外部函数符号，不在程序刚装载时就解析其最终地址，而是在**第一次真正调用**时完成解析。

典型流程：

1. 程序执行 `call ext@plt` 一类调用。
2. 如果 `ext` 尚未绑定，该 PLT/GOT 路径进入动态链接器。
3. 动态链接器定位实际函数，保存解析结果。
4. 第一次调用跳到函数实现；以后同一调用可直接沿已更新的表项跳转，避免重新解析。

> [!note] 课内 IA-32 的 GOT/PLT 结构
> 传统 32 位 ELF 的典型例子把 `GOT[0]`、`GOT[1]`、`GOT[2]` 用于动态链接器协作，并用后续表项对应外部函数；PLT 中还存在公共入口 `PLT[0]`。这能帮助理解**首次调用与后续调用为何不同**，但 GOT 索引、PLT 指令长度和入口机器码都不是不同 CPU 架构通用的固定值。

> [!warning] 延迟绑定并非所有程序都启用
> 现代环境可使用立即绑定、完全 RELRO 等安全配置，某些架构或编译选项也使用不同的调用模型。比如链接器选项 `-Wl,-z,now` 常用于要求启动阶段尽早解析动态符号。理解“lazy binding”时，应把它看成**一种可能采用的策略**，而不是所有 `.so` 的唯一工作方式。

### 7. GOT 与 PLT 一次辨析

| 比较项 | GOT | PLT |
| --- | --- | --- |
| 名称 | Global Offset Table | Procedure Linkage Table |
| 主要形态 | 保存地址等动态链接相关数据的表 | 由跳转/调用相关代码组成的入口表 |
| 典型用途 | 间接获得外部变量或函数地址 | 将外部函数调用导向正确实现 |
| 一般位置 | 可写或经重定位后受保护的数据区域 | 可执行代码区域 |
| 与延迟绑定关系 | 可保存已绑定的函数地址 | 可引导首次未绑定调用进入解析过程 |

> [!tip] 一句话记忆
> **GOT 主要记“地址在哪里”，PLT 主要管“函数怎么跳过去”。** 两者经常协作，但不是同一张表。

## 十、调试链接问题的实用工具

### 1. 常用命令速查

| 命令 | 重点查看什么 |
| --- | --- |
| `gcc -c source.c` | 分离编译，得到 `.o` |
| `gcc a.o b.o -o app` | 将多个目标模块链接成程序 |
| `readelf -h file` | ELF 头和文件类型 |
| `readelf -S file` | 节头表与节布局 |
| `readelf -s file` | 符号表、`UND`、绑定类别 |
| `readelf -r file` | 重定位类型、偏移、相关符号 |
| `readelf -l file` | 程序头表与装入段 |
| `readelf -d file` | 动态段、共享库依赖 |
| `objdump -d file` | 反汇编机器指令 |
| `objdump -dr file.o` | 反汇编并结合重定位记录分析 |
| `nm file.o` | 紧凑查看符号定义与引用 |
| `ar -t libname.a` | 显示静态库的目标成员 |

### 2. 报错时如何判断是哪一环出了问题

| 常见报错或现象 | 首先检查 |
| --- | --- |
| `undefined reference to 'foo'` | 是否只有声明没有定义；定义所在 `.o` / 库是否参与链接；静态库是否在正确顺序 |
| `multiple definition of 'x'` | 是否多个源文件定义同名全局变量；是否在头文件中错误定义变量；是否遇到 `-fno-common` |
| `cannot find -lxxx` | 库文件是否存在；名称是否遵循 `libxxx.*`；`-L` 搜索路径是否正确 |
| 运行时提示 `libxxx.so: cannot open shared object file` | 运行时动态库搜索路径、`RUNPATH` / `RPATH`、环境与部署目录 |
| `undefined symbol`（运行时） | 共享库版本是否兼容；是否导出所需符号；是否链接到错误版本 |
| 程序能链接却结果异常 | 是否存在错误的外部变量类型声明、ABI 不兼容或未定义行为 |

**典型排查顺序：**先确认目标文件和库是否生成 → 看 `nm` / `readelf -s` 是否存在目标符号 → 检查命令行顺序与依赖 → 再检查重定位、库搜索路径或 ABI。

### 3. 推荐的分层实验方法

不要一开始就试图理解几十个源文件的工程。先用**两个源文件**观察链接，再把其中一个文件打包成 `.a`，最后改成 `.so`，会更容易定位每次发生的变化。

- 第一步：观察 `main.o` 里的 `UND` 符号和重定位记录。
- 第二步：链接 `main.o swap.o`，观察可执行文件的程序头表。
- 第三步：自己创建 `.a`，故意交换命令行顺序，观察是否出现未定义引用。
- 第四步：创建 `.so`，查看 `INTERP`、`NEEDED` 和运行时库搜索路径。
- 第五步：使用 `dlopen` / `dlsym`，体验运行时才根据名字获得函数地址。

## 十一、典型练习与参考思路

> [!question] 练习 1：目标文件分类
> `.o`、普通可执行文件、`.so`、`.a` 的角色有何不同？ELF 的“节”和“段”分别面向什么需求？

**提示**：先区分能否直接运行、是否还要进一步链接；再判断 `.a` 是目标文件还是归档。

> [!question] 练习 2：判断符号
> 在双文件示例中，`main.o` 的 `swap`、`swap.o` 的 `buf` 和 `bufp1` 分别属于什么类型的符号？为何 `temp` 通常不属于普通的链接器局部符号？

**提示**：先看符号是否在**本模块定义**，再看它是否对其他模块可见。

> [!question] 练习 3：链接顺序
> `main.o` 引用 `foo`，`libx.a` 中某个成员定义 `foo`。对于传统从左到右扫描的静态链接器，下面两种命令有何区别？
>
> ```bash
> gcc main.o libx.a -o app
> gcc libx.a main.o -o app
> ```

**提示**：想象扫描到每个归档时，当前尚未解析的符号集合 `U` 里是否已经包含 `foo`。

> [!question] 练习 4：计算 PC 相对位移
> 假定 `call` 指令从地址 `0x1000` 开始，总长 5 字节，目标函数位于 `0x1014`，问写入的有符号 32 位相对位移是多少？

**参考解**：下一条指令地址为 `0x1005`，因此偏移是 `0x1014 - 0x1005 = 0xF`，即十进制 **15**；位移字段按小端序存为 `0F 00 00 00`。

> [!question] 练习 5：数据段占用
> 一个 `PT_LOAD` 段满足 `p_filesz=0x120`、`p_memsz=0x148`，其运行时需要额外零填充多少字节？

**参考解**：`0x148 - 0x120 = 0x28 = 40` 字节。

> [!question] 练习 6：GOT 与 PLT
> 当程序调用尚未解析的共享库函数时，为什么可能先跳到 PLT？为什么第一次调用比后续调用多出解析过程？

**提示**：PLT 负责调用跳转路径，GOT 存放相关地址表项；延迟绑定首次调用时更新表项。

## 十二、章节总结与速查

> [!summary] 核心知识网络
> - **目标文件**：`.o` 用于继续链接；可执行 ELF 用于加载；`.so` 用于动态链接；`.a` 是多个 `.o` 的归档。
> - **ELF 两种视图**：链接看**节**、节头表；加载看**段**、程序头表。
> - **关键节**：`.text` 是代码，`.rodata` 是只读数据，`.data` 是已初始化数据，`.bss` 是通常不逐字节存盘的零初始化数据，`.symtab` 是符号信息，`.rel*` / `.rela*` 是重定位信息。
> - **符号解析**：建立符号引用和定义之间的关联，注意跨文件全局变量及多重定义。
> - **重定位**：确定合并后符号的地址，再修改引用地址字段；IA-32 的 `R_386_32` 对应 $S+A$，`R_386_PC32` 对应 $S+A-P$。
> - **静态库**：按需抽取成员，传统链接顺序为“先引用，后提供定义”。
> - **程序加载**：按照 `PT_LOAD` 等程序头建立虚拟内存映射；`e_entry` 通常指向 `_start` 而不是 `main`。
> - **动态链接**：加载时或运行时接入共享库；PIC 用相对寻址和间接地址表提高代码可共享性；GOT/PLT 可协同实现外部访问与延迟绑定。

### 必须区分的八组概念

| 容易混淆 | 正确区分 |
| --- | --- |
| 编译 vs. 链接 | 编译生成单个模块的目标表示；链接组合模块并处理符号引用与地址 |
| 声明 vs. 定义 | 声明提供接口信息；定义提供实体或函数实现 |
| 符号解析 vs. 重定位 | 找到定义 vs. 确定并写入地址 |
| 全局符号 vs. 链接器局部符号 | 可供其他模块引用 vs. 仅在当前模块内部使用 |
| common 暂定定义 vs. `WEAK` 绑定 | 传统未初始化变量处理方式 vs. ELF 的独立符号绑定类型 |
| 文件偏移 vs. 虚拟地址 | 文件中的字节位置 vs. 进程虚拟空间中的位置 |
| 节 Section vs. 段 Segment | 链接处理单位 vs. 加载映射单位 |
| GOT vs. PLT | 保存地址的表 vs. 用于间接函数调用/跳转的代码入口 |

> [!important] 最终自检
> 能否解释：**为什么 `main.c` 可以只声明 `swap` 就调用它；为什么 `swap.o` 不知道 `buf` 的最终地址仍可以先编译；为什么静态库顺序会造成链接失败；为什么 `.bss` 不占相同长度的文件空间却需要运行时内存；为什么共享库需要 PIC、GOT 和 PLT。**
>
> 如果能把这五个问题的前因后果讲清楚，就基本建立了本章完整的知识联系。
