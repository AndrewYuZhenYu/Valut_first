# 第五章 程序的执行

> [!abstract] 本章知识主线
> **程序由指令组成 → PC 决定下一条指令 → CPU 通过数据通路与控制单元完成指令 → 多条指令采用流水线重叠执行 → 冒险限制并行 → 编译器与高级微体系结构提高吞吐率。**
>
> 学习重点：**指令执行五步、CPU 内部部件、流水线时序与性能计算、三类冒险、CISC/RISC、超流水线与多发射。**

## 一、程序怎样在 CPU 上执行

### 1. 程序、指令与执行流

**程序**是按一定逻辑组织起来的机器指令序列。指令最终以二进制形式保存在存储器中；CPU 不直接执行 C/C++ 源代码，而是执行编译、汇编、链接后形成的机器指令。

- **顺序执行**：一般情况下，CPU 顺着指令存放的地址依次执行。
- **改变执行流**：无条件转移、条件转移、函数调用、函数返回等指令会使下一条指令的地址改变。
- **程序计数器 PC（Program Counter）**：保存下一条将要获取的指令地址；在 IA-32 中，对应 **EIP** 寄存器。
- **指令周期**：取出并执行一条指令所涉及的过程或时间；不要简单等同于一个时钟周期。

> [!important] PC 的核心作用
> **CPU 通过更新 PC 来控制程序执行顺序。**
>
> - 顺序执行：`PC ← PC + 当前指令长度`。
> - 分支跳转：`PC ← 目标地址`（可能取决于条件是否成立）。
> - 函数调用：保存返回地址，再将 PC 改为被调函数入口。
> - 函数返回：取回保存的返回地址，恢复到调用点之后继续执行。
>
> `PC + 1` 中的“1”有时仅指“**一条指令的长度**”，不意味着 PC 必然只增加 1 个字节。对固定 32 位指令、按字节寻址的 MIPS 示例，顺序执行通常是 `PC + 4`。

### 2. 函数调用为何会改变执行顺序

观察一段 C 语言程序：

```c
#include <stdio.h>

void outputs(const char *str) {
    printf("%s\n", str);   // 输出收到的字符串
}

int main(int argc, char *argv[]) {
    if (argc > 1) {       // 确保命令行确实提供了字符串参数
        outputs(argv[1]); // 调用函数，执行流跳入 outputs
    }
    return 0;             // 函数返回后，执行流回到这里
}
```

执行时不会把 `outputs` 函数“复制到” `main` 中，而是通过调用、返回指令完成控制流切换。若 `outputs` 内部再调用 `printf`，便形成多层嵌套调用。

**调用栈（栈帧）**用来保存返回地址及与调用有关的局部信息（具体布局依赖体系结构、调用约定和编译器）。常见的 32 位 x86 函数序言、结尾是：

```asm
push %ebp           # 保存调用者的基址寄存器
mov  %esp, %ebp     # 将当前栈顶作为本函数栈帧基址
sub  $0x18, %esp    # 在栈上预留 24 字节空间
# 此处省略函数体；该行仅为注释，不代表一条机器指令
leave               # 恢复栈帧，相当于 mov %ebp,%esp; pop %ebp
ret                 # 弹出返回地址，返回调用者
```

此处使用课件中的 **GNU/AT&T 风格 IA-32 汇编**：寄存器加 `%`，立即数加 `$`，多数双操作数指令的顺序是“源、目的”。以上代码片段用于解释栈帧，不是独立程序。

> [!warning] 栈帧示例中的字符串复制风险
> 课件还使用了 `char buffer[16]; strcpy(buffer, str);` 说明调用过程。该代码**无法检查源字符串长度**，长字符串可能造成缓冲区溢出。若教学目的只是复制字符串，可使用限定长度的方式，例如：
>
> ```c
> char buffer[16];
> snprintf(buffer, sizeof(buffer), "%s", str); // 最多写入15个可见字符并保留终止符
> ```
>
> 本例假定已包含 `<stdio.h>`、`str` 指向有效的以 `\0` 结尾的字符串。使用更安全的写法不会改变“函数调用与返回机制”的原理。

### 3. 机器代码与汇编代码的关系

**汇编语言是机器指令的符号化表示**：每条指令由操作码、操作数或其描述字段等构成，CPU 实际读取的是编码后的 0/1 序列。

课件中的 IA-32 `add` 函数反汇编片段：

```asm
push %ebp           # 机器码 55：保存旧栈帧基址
mov  %esp, %ebp     # 机器码 89 e5：建立新栈帧
mov  0xc(%ebp), %eax # 机器码 8b 45 0c：将第二个参数读入 EAX
add  0x8(%ebp), %eax # 机器码 03 45 08：将第一个参数加到 EAX
pop  %ebp           # 机器码 5d：恢复旧基址
ret                 # 机器码 c3：返回调用者
```

上述 `0x8(%ebp)` 与 `0xc(%ebp)` 是**基址加位移寻址**：它们表示以 `EBP` 为基准、偏移分别为 8 和 12 字节的内存位置，并非把 `0x8` 和 `0xc` 两个立即数直接相加。该参数位置仅适用于所示调用约定及栈帧形式。

| 机器码字节 | 汇编指令 | 指令长度 |
| --- | --- | ---: |
| `55` | `push %ebp` | 1 字节 |
| `89 e5` | `mov %esp,%ebp` | 2 字节 |
| `8b 45 0c` | `mov 0xc(%ebp),%eax` | 3 字节 |
| `03 45 08` | `add 0x8(%ebp),%eax` | 3 字节 |
| `5d` | `pop %ebp` | 1 字节 |
| `c3` | `ret` | 1 字节 |

> [!note] CPU 在指令译码时需要回答哪些问题？
> - **指令边界**：这一条指令到哪里结束，下一条从哪里开始？
> - **操作类型**：是加载、存储、算术、分支还是函数调用？
> - **操作数位置**：数据来自寄存器、立即数字段还是存储器？
> - **寻址方式**：是否需要计算有效地址？
> - **控制信号**：应启用哪个部件，以及将结果写回何处？
>
> 变长指令集的解析通常比定长指令集复杂；同一个操作的汇编助记符也可能对应不同机器编码。

## 二、CPU 的基本功能与内部组成

### 1. CPU 的两类基本工作

CPU 执行程序的主要活动分为：

1. **CPU 内部操作**：寄存器传送、译码、算术逻辑运算、地址计算、条件判定等。
2. **访存和 I/O 操作**：从存储器取指、读写数据，或通过相关接口与外设交换信息。

CPU 的基本功能不只是算术运算，还包括**控制指令执行流、响应异常与中断**。

### 2. 数据通路与控制单元

CPU 可以从功能上划分为两个基本部分：

- **数据通路（Datapath）**：用于存放、传送、处理数据。它决定数据“能够经过哪些部件、沿哪条路径流动”。
- **控制单元（Control Unit）**：译码指令，并综合条件标志、机器状态和时序信号，产生控制数据通路的信号。它决定数据“什么时候流动、做什么操作”。

![CPU结构及寄存器](./第五章_程序的执行_配图/CPU结构及寄存器.png)

| 部件 | 英文 / 缩写 | 主要功能 |
| --- | --- | --- |
| 程序计数器 | PC | 提供待取指令的地址 |
| 指令寄存器 | IR | 保存当前取得、准备译码的指令或相关指令信息 |
| 主存地址寄存器 | MAR | 保存本次存储器访问的地址 |
| 主存数据寄存器 | MDR | 缓存本次存储器访问读取或写入的数据 |
| 通用寄存器组 | GPRs | 保存操作数、地址和中间结果 |
| 算术逻辑单元 | ALU | 完成加减、比较、逻辑运算等 |
| 标志寄存器 | Flags | 保存运算结果相关标志，如零标志、进位等 |
| 控制器 | Control Unit | 产生读写、选择、运算、分支等控制信号 |

> [!tip] 记忆内部部件
> **PC 管“去哪条指令”；IR 管“当前是什么指令”；MAR 管“访问哪个地址”；MDR 管“传输什么数据”；ALU 管“怎样计算”；控制器管“怎样协调”。**
>
> 上图是教学用的概念模型。现代处理器可以采用更复杂的寄存器、缓存、总线和流水结构，不必都设置与图中同名的独立物理寄存器。

### 3. 组合逻辑元件与状态元件

| 分类 | 主要成员 | 核心特征 |
| --- | --- | --- |
| **组合逻辑** | 加法器、ALU、扩展器、多路选择器（MUX）等 | 当前输出主要由当前输入决定；不直接保存历史状态 |
| **状态元件** | 触发器、寄存器、存储器等 | 能保持信息，保存中间或最终结果 |

**时钟信号**用于同步状态更新。在同步设计中，数据通常在周期内经过组合逻辑，并在规定的时钟沿被寄存器保存。

> [!example] 一次寄存器加法中的信息流
> 假设要计算 `R1 = R2 + R3`：
>
> 1. 控制单元选择寄存器 `R2` 和 `R3` 作为源操作数。
> 2. 两个源值通过数据通路送到 ALU 输入端。
> 3. 控制单元要求 ALU 做加法。
> 4. ALU 输出结果；在合适的时序下写回 `R1`。
>
> **“寄存器→ALU→寄存器”是数据路径；“选择源寄存器、选择加法、允许写回”是控制信息。**

### 4. IA-32 的寄存器组织

- `EAX`、`EBX`、`ECX`、`EDX` 等是 32 位通用寄存器。
- `AX` 是 `EAX` 的低 16 位；`AH`、`AL` 分别表示 `AX` 的高 8 位、低 8 位。
- `ESP` 常用于记录栈顶；`EBP` 在传统栈帧方案中常用作帧基址。
- `ST(0)~ST(7)` 关联 x87 浮点寄存器栈；`MM0~MM7` 是与 x87 寄存器物理存储共享的 MMX 视图；`XMM` 是 SIMD 寄存器。

这些寄存器展示了 x86 历史上**扩展字长并努力保持指令兼容**的发展过程；不能误以为所有不同名称都是互不相关的独立硬件寄存器。

## 三、一条机器指令的执行过程

### 1. 从取指到写回

课堂中可以将一条指令的执行分解为下列逻辑步骤：

1. **取指（Instruction Fetch）**：根据 PC，从存储器或指令缓存取得指令。
2. **PC 更新**：计算顺序执行时的下一地址；变长指令可能需要先识别指令长度。
3. **译码（Decode）**：识别操作码、寄存器编号、操作数类型和控制需求。
4. **源操作数地址计算**：按寄存器、立即数、基址加位移等寻址方式处理。
5. **读取源操作数**：从寄存器或存储器取数。
6. **执行操作**：由 ALU、加法器或其他功能部件完成运算。
7. **结果写回**：把结果写入寄存器或存储器（视指令种类而定）。
8. **控制流确认**：根据分支条件等，确定真正的后续执行地址。

> [!warning] 逻辑步骤不等于严格固定的物理先后顺序
> 这是一种**理解指令语义的分解方式**，并不意味着每条指令都执行上述每一步，也不意味着每个步骤占一个独立时钟周期。取操作数、地址计算、译码等可能合并或重叠。存储器写入与寄存器写回也不是同一回事。

### 2. 四类基本数据操作

从数据通路角度，不同机器指令可归结为以下基本操作的组合：

| 基本操作 | 典型用途 |
| --- | --- |
| **内存 → 寄存器** | 取指、取内存中的操作数 |
| **寄存器 → 内存** | 将结果存入主存 |
| **寄存器 → 寄存器 / ALU** | 传送操作数、准备运算 |
| **算术或逻辑运算** | 加减、比较、逻辑运算、地址计算、PC 更新 |

用于描述寄存器之间数据传送的语言称为**寄存器传送语言（RTL，Register Transfer Language）**。

以下等式**是 RTL 语义表达，不是程序代码**：

$$
\begin{aligned}
\mathrm{IR}&\leftarrow M[\mathrm{PC}]\\
\mathrm{R1}&\leftarrow\mathrm{R2}+\mathrm{R3}\\
\mathrm{PC}&\leftarrow\mathrm{PC}+4
\end{aligned}
$$

其中 $M[x]$ 表示地址 $x$ 对应的存储器内容；最后一式只适用于**当前顺序执行步长为 4 字节**的情况。

### 3. 一段指令的逐步理解

用 MIPS 风格的真实汇编指令观察访存和运算：

```asm
lw  $8, 0($2)       # 读取内存[$2+0]中的一个字，放入寄存器$8
lw  $9, 4($2)       # 读取内存[$2+4]中的一个字，放入寄存器$9
add $10, $8, $9    # ALU计算$8+$9，写到寄存器$10
sw  $10, 8($2)     # 将$10的内容写入内存[$2+8]
```

- `lw` / `sw` 是访存指令，需要计算有效地址。
- `add` 是寄存器运算指令，典型的 Load/Store 架构不允许这条 `add` 直接从内存取操作数。
- 四条指令都需要取指和译码，但所使用的其他数据通路可能不同。
- 此例假定访问地址按字对齐、寄存器和内存中有有效数据，暂不讨论溢出、缓存缺失与异常。

### 4. 异常与中断

执行指令时，CPU 必须处理非正常控制流：

| 比较项目 | 异常（Exception） | 中断（Interrupt） |
| --- | --- | --- |
| 典型来源 | 指令执行中检测出的情况 | 外部设备或系统事件提出的请求 |
| 典型例子 | 除零、非法指令、缺页等 | 定时器、I/O 设备通知等 |
| 与当前指令关系 | 往往与正在执行的指令有关 | 通常异步于当前指令流 |
| 处理方法 | 转入相应异常处理程序 | 在适当时机进入中断处理程序 |

> [!note] 必要辨析
> 课件采用“**内部异常 / 外部中断**”的入门划分。实际体系结构中，陷阱、故障、软件触发的中断等存在更细的分类，不宜把“异常一定由硬件故障引起”或“中断一定立即打断任意半条指令”当成绝对规则。

## 四、从串行执行到指令流水线

### 1. 为什么需要流水线

传统**串行方式**下，一批任务从头到尾完成后，才开始下一批任务。这样一来，不同功能部件会有大量等待时间。**流水线（Pipeline）**把任务分成若干阶段，使不同任务在不同阶段**重叠执行**。

流水线的核心不是缩短每项任务的所有处理时间，而是让不同阶段在同一时刻处理不同任务，从而提高**单位时间完成的任务数（吞吐率）**。

### 2. 洗衣服示例：理解流水线为什么快

假设每批衣物依次完成三个阶段：

| 阶段 | 洗衣 | 烘干 | 折叠 |
| --- | ---: | ---: | ---: |
| 每批用时 | 30 min | 40 min | 20 min |

**串行方式**：每批总耗时 $30+40+20=90$ 分钟，$N$ 批衣物需要：

$$
T_{\text{串行}}=N(30+40+20)=90N\;\mathrm{min}
$$

**流水方式**：第一批一旦进入烘干阶段，洗衣机便可开始第二批；每批在不同设备上向前推进。烘干最慢，成为流水线的**瓶颈阶段**。在不冲突、任务连续到达的情况下：

$$
T_{\text{流水}}=30+40N+20=40N+50\;\mathrm{min}
$$

> [!example] 四批衣服需要多久？
> - 串行：$4\times90=360\;\mathrm{min}=6\;\mathrm{h}$。
> - 流水：$30+4\times40+20=210\;\mathrm{min}=3.5\;\mathrm{h}$。
> - 加速比：$S=360/210\approx1.714$。
>
> 注意：**“分三段”不代表处理四批就一定加速三倍。** 阶段时间不均衡、流水线启动和排空，都影响实际效果。

> [!important] 从洗衣模型抽象出的结论
> 一条流水线能够稳定接收新任务的间隔，通常不能小于**最慢阶段的执行时间**。当任务数足够多时，总完成时间主要由最慢阶段控制。

### 3. 指令流水线的五个逻辑阶段

课件先给出一种便于理解的五段划分：

| 阶段 | 英文 | 作用 |
| --- | --- | --- |
| **IF** | Instruction Fetch | 根据 PC 取出指令 |
| **ID** | Instruction Decode | 译码并生成控制信号 |
| **OF** | Operand Fetch | 取得寄存器或存储器中的操作数 |
| **EX** | Execute | 完成指定运算 |
| **WB** | Write Back | 将结果写回相应位置 |

![五段流水线的基础时序](./第五章_程序的执行_配图/五段流水线时序.png)

在讨论 **MIPS 风格的实际五段流水线数据通路**时，课件采用更常见的划分：

| 流水段 | 英文 | 主要工作 |
| --- | --- | --- |
| **IF** | Instruction Fetch | 取指、产生顺序地址 |
| **ID** | Instruction Decode / Register Read | 译码、读取寄存器 |
| **EX** | Execute / Address Calculation | ALU 运算或计算数据访问地址 |
| **MEM** | Memory Access | 访存指令读写数据存储器；其他指令经过此阶段 |
| **WB** | Write Back | 将需要写回的结果写入寄存器 |

> [!warning] 两种“五段”不要混为一谈
> **IF–ID–OF–EX–WB** 是对指令执行逻辑的简化分段；**IF–ID–EX–MEM–WB** 是课件后面讨论的典型 MIPS 五段微体系结构，其中读寄存器并入 ID，MEM 单独成为一段。
>
> 两者都能帮助理解流水线，但**计算数据冒险和绘制具体时序图时必须使用对应的同一套分段**，不可任意拼接。

### 4. 五段流水线如何重叠执行

无相关冲突且每段占一个周期时，四条指令的理想时序是：

| 指令 | 周期1 | 周期2 | 周期3 | 周期4 | 周期5 | 周期6 | 周期7 | 周期8 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| $I_1$ | IF | ID | EX | MEM | WB | | | |
| $I_2$ | | IF | ID | EX | MEM | WB | | |
| $I_3$ | | | IF | ID | EX | MEM | WB | |
| $I_4$ | | | | IF | ID | EX | MEM | WB |

第 4 个周期内，CPU 的不同功能段同时处理不同指令：

- $I_1$ 在 MEM；
- $I_2$ 在 EX；
- $I_3$ 在 ID；
- $I_4$ 在 IF。

**同一时刻多条指令处于不同执行阶段**，不代表一条指令可以在一个周期里跳过所有阶段。

> [!important] 五段流水线的总周期数
> 对 $k$ 段流水线、$N$ 条连续且无冒险的指令，每段每周期前进一级，理想情况下：
>
> $$
> \boxed{C=N+k-1}
> $$
>
> 因此从空流水线开始，$N$ 条指令完成所需时间为：
>
> $$
> \boxed{T_{\text{流水}}=(N+k-1)\,t_{\text{clk}}}
> $$
>
> 第一条指令要经历 $k$ 个周期；后续在稳定运行时可**每周期完成一条**。上述公式不包含额外阻塞、冲刷和变长延时。

### 5. 吞吐率、延迟、CPI 与 IPC

四个概念必须严格区分：

| 概念 | 定义 | 关键解释 |
| --- | --- | --- |
| **时钟周期** $t_{\text{clk}}$ | 相邻有效时钟沿之间的时间 | 越短，频率通常越高 |
| **指令延迟（Latency）** | 单条指令从进入至完成的时间 | 流水线不一定使它变短 |
| **吞吐率（Throughput）** | 单位时间完成的指令条数 | 流水线最主要的收益指标 |
| **CPI** | 平均每条指令占用的时钟周期数 | $\mathrm{CPI}=\frac{\text{总周期数}}{\text{指令数}}$ |
| **IPC** | 平均每时钟周期完成的指令数 | $\mathrm{IPC}=\frac{\text{指令数}}{\text{总周期数}}=1/\mathrm{CPI}$ |

有以下关系：

$$
\begin{aligned}
T_{\text{程序}}&=N\times\mathrm{CPI}\times t_{\text{clk}}\\
\text{指令吞吐率}&=\frac{\mathrm{IPC}}{t_{\text{clk}}}=\frac{1}{\mathrm{CPI}\,t_{\text{clk}}}
\end{aligned}
$$

> [!note] CPI 和 IPC 何时取 1？
> - 理想单发射五段流水线在稳态每周期完成一条指令，长期平均 **CPI 接近 1，IPC 接近 1**。
> - 有停顿或冲刷时，**CPI 大于 1、IPC 小于 1**。
> - 多发射处理器在合适条件下能使 **CPI 小于 1、IPC 大于 1**。
> - 流水线启动与排空也会影响短程序的平均 CPI，因此不能无条件说“所有流水线的 CPI 都等于 1”。

## 五、单周期处理器与流水线处理器的性能计算

### 1. 课件的同一组时延条件

假定一条较复杂指令需要经历以下五步：

| 阶段 | IF | ID / 读寄存器 | EX | MEM | WB |
| --- | ---: | ---: | ---: | ---: | ---: |
| 组合逻辑耗时 | 200 ps | 50 ps | 100 ps | 200 ps | 50 ps |

同时假设流水段寄存器的时序开销为 **50 ps**。此处的 $\mathrm{ps}$ 是皮秒：

$$1\;\mathrm{ps}=10^{-12}\;\mathrm{s}$$

### 2. 单周期数据通路

单周期处理器要求每条指令**在一个时钟周期内完成**，因此时钟周期必须容纳最慢指令的完整组合逻辑路径以及必要的寄存器时序开销：

$$
\begin{aligned}
t_{\text{clk,单}}&=200+50+100+200+50+50\\
&=600\;\mathrm{ps}
\end{aligned}
$$

- CPI = 1。
- 单条指令延迟 = 600 ps。
- 理想吞吐率：

$$
\frac{1}{600\times10^{-12}}\approx1.67\times10^9\;\text{条/秒}
=\boxed{1.67\;\mathrm{GIPS}}
$$

执行 $N$ 条指令：

$$T_{\text{单}}=600N\;\mathrm{ps}$$

这里的 GIPS 是 **Giga Instructions Per Second，即十亿条指令每秒**。

### 3. 五段流水线数据通路

五个组合逻辑阶段中，最长的是 **200 ps**。每段后需要流水段寄存器，假设寄存器时序开销 50 ps，则：

$$
\boxed{t_{\text{clk,流水}}=200+50=250\;\mathrm{ps}}
$$

第一条指令穿过五段的延迟：

$$
\boxed{L_{\text{单条}}=5\times250=1250\;\mathrm{ps}=1.25\;\mathrm{ns}}
$$

稳定运行、每周期完成一条指令时，吞吐率是：

$$
\boxed{\text{Throughput}=\frac{1}{250\times10^{-12}}=4\times10^9\;\text{条/秒}=4\;\mathrm{GIPS}}
$$

执行 $N$ 条无冒险指令的总时间：

$$
\boxed{T_{\text{流水}}=(N+4)\times250\;\mathrm{ps}}
$$

> [!warning] 最容易混淆的一组结果
> **单周期处理器**：单条指令延迟 $600\;\mathrm{ps}$，吞吐率 $1.67\;\mathrm{GIPS}$。
>
> **五段流水线**：单条指令延迟 $1250\;\mathrm{ps}$，吞吐率 $4\;\mathrm{GIPS}$。
>
> 这不矛盾：流水线让**一条指令的总延迟变长**，但使**许多指令重叠执行时的完成速率提高**。

### 4. 加速比怎样计算

定义：

$$S=\frac{T_{\text{原方案}}}{T_{\text{新方案}}}$$

课件这组条件下：

$$
S(N)=\frac{600N}{250(N+4)}
$$

> [!example] 实际计算：4 条指令
> $$
> T_{\text{单}}=4\times600=2400\;\mathrm{ps}
> $$
>
> $$
> T_{\text{流水}}=(4+4)\times250=2000\;\mathrm{ps}
> $$
>
> $$
> S=\frac{2400}{2000}=\boxed{1.2}
> $$
>
> 只有四条指令，流水线还未充分发挥优势；增加指令条数后，启动和排空开销相对减少。

当 $N$ 很大时：

$$
\lim_{N\to\infty}S(N)=\frac{600}{250}=\boxed{2.4}
$$

**为什么不是 5？** 因为各段原始延迟不均衡（50、100、200 ps），且每段有 50 ps 的寄存器开销。**“五段可提高约五倍”必须建立在阶段平衡、流水开销很小、指令足够多且无冒险的理想条件上。**

> [!tip] 计算题通用步骤
> 1. 看清**是否存在流水段寄存器开销**。
> 2. 单周期：计算最长指令的完整组合路径，再考虑寄存器开销。
> 3. 流水线：先求 `最大流水段延时 + 流水寄存器开销`。
> 4. 无冒险 $N$ 条指令：总周期数 $N+k-1$。
> 5. 最后再求延迟、吞吐率、加速比，**不要混用单指令延迟与稳态吞吐率**。

## 六、怎样设计和实现指令流水线

### 1. 适合流水线的指令集特征

流水线要求不同指令尽量以类似的步骤使用硬件。指令集若具有以下特征，通常更容易实现高效流水：

1. **指令长度规整**：便于确定取指边界和下一条地址，例如固定 32 位 MIPS 指令，顺序地址通常直接加 4。
2. **指令格式少、字段位置相对固定**：译码时容易找到源寄存器编号，减少各级协调难度。
3. **Load/Store 分离**：主要由专门访存指令读写存储器，算术逻辑指令在寄存器中运算，使各段职责相对统一。
4. **内存访问对齐**：减少一次访问跨越存储边界等带来的复杂性（具体要求依指令集和实现而异）。

> [!important] 核心设计思想
> **规整、简单、一致**有利于高效率的指令流水线：易取指、易译码、易预测延迟、易分配硬件资源。

### 2. MIPS 指令格式的实例

课件以 MIPS 典型 R 型指令说明：

| 字段 | op | rs | rt | rd | shamt | funct |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 位数 | 6 | 5 | 5 | 5 | 5 | 6 |

六个字段共 **32 位**。

- `op`：操作码字段。
- `rs`、`rt`：典型指令使用的源寄存器字段（具体角色需看指令类型）。
- `rd`：R 型运算的目标寄存器字段。
- `shamt`：移位量。
- `funct`：与操作码一起确定具体运算。

> [!note] 不能死背“rs 和 rt 一定是两个源寄存器”
> **字段位置固定**不代表字段的语义在所有指令中都完全相同。例如 I 型的 `lw` 往往把 `rt` 当作装入结果的目标寄存器，而不是第二源寄存器。

### 3. CISC 与 RISC

指令集体系结构（ISA）可按传统设计风格分为：

- **CISC（Complex Instruction Set Computer）**：复杂指令集计算机。
- **RISC（Reduced Instruction Set Computer）**：精简指令集计算机。

| 对比角度 | 传统 CISC 风格 | 传统 RISC 风格 |
| --- | --- | --- |
| 指令数量与复杂性 | 指令较丰富、部分指令功能复杂 | 强调简单、规整的常用操作 |
| 指令长度 | 常见变长指令 | 倾向定长或较规整的编码 |
| 寻址方式 | 往往较丰富 | 往往较少 |
| 内存操作 | 部分算术指令可直接使用内存操作数 | 通常仅 Load/Store 直接访问数据存储器 |
| 运算操作 | 可能混合寄存器与内存操作 | 倾向寄存器-寄存器（RR）运算 |
| 控制实现 | 传统设计多使用微程序 | 传统设计强调硬布线控制 |
| 编译器作用 | 指令选择与优化较复杂 | 通常更强调编译器的调度与优化 |
| 代表 | x86 历史上主要体现 CISC 风格 | MIPS 是课件的典型例子 |

**课件介绍的历史背景**：对早期复杂指令系统的统计发现，频繁使用的往往是较简单的指令，复杂指令占用了较多硬件或控制存储器资源，却未必被经常调用。因此出现了精简指令系统的设计思路。

课件列出的某组 80x86 指令执行频率调查如下：

| 指令类型 | 频率 | 指令类型 | 频率 |
| --- | ---: | --- | ---: |
| 从内存加载到寄存器 `MOV` | 22% | 条件转移 `Jcc` | 20% |
| 比较 `CMP` | 16% | 寄存器写入内存 `MOV` | 12% |
| 加法 `ADD` | 8% | 逻辑与 `AND` | 6% |
| 减法 `SUB` | 5% | 寄存器间传送 | 4% |
| 调用 `CALL` | 1% | 返回 `RET` | 1% |

合计 **96%**。这是一组**课件引用的历史示例数据**，用于说明简单常用指令占据大量动态执行次数，不代表所有现代程序都具有同样的分布。

> [!warning] 避免对 CISC / RISC 的绝对化理解
> **RISC 不等于一定比 CISC 快，CISC 不等于不能流水线。** 现代 x86 内核也可将复杂 ISA 指令译为内部较简单的微操作，再使用高效流水线、预测和乱序调度；现代 RISC 处理器也可以使用复杂执行单元。两者是设计风格，不可直接当作性能排名。
>
> 课件提到的“x86 指令长度 1～17 字节”不宜当作现代 x86 的通用规定；常见 IA-32/x86-64 架构下**单条机器指令最长为 15 字节**（超过限制的编码不作为合法指令），具体 ISA 和编码规则要以对应架构文档为准。

### 4. 五段流水线的数据通路

![五段流水线数据通路](./第五章_程序的执行_配图/五段流水线数据通路.png)

流水线不仅是五个功能块排在一起，还需要在段与段之间放置**流水段寄存器（Pipeline Registers）**，保存每个周期的阶段输出：

| 流水段寄存器 | 位置 | 典型保存内容 |
| --- | --- | --- |
| `IF/ID` | IF 与 ID 之间 | 指令编码、后继地址信息等 |
| `ID/EX` | ID 与 EX 之间 | 寄存器值、立即数、目标寄存器信息、控制信号等 |
| `EX/MEM` | EX 与 MEM 之间 | ALU 结果、存储数据、条件及控制信息等 |
| `MEM/WB` | MEM 与 WB 之间 | 内存读取数据或 ALU 结果、目标寄存器及写回控制信息等 |

> [!important] 为什么不能只传送“计算结果”？
> 一条指令经过各段时，需要的不只是操作数。例如 `lw` 在 MEM 取得数据之后，WB 还必须知道**应写入哪个目标寄存器**、**写回是否使能**。所以流水段寄存器会同时传递数据、指令字段和相应控制信号。

典型数据流（属于概念描述，具体实现可能不同）：

- `lw`：**IF → ID（读基址寄存器）→ EX（算地址）→ MEM（读内存）→ WB（写寄存器）**。
- `sw`：**IF → ID（读基址和待写数据）→ EX（算地址）→ MEM（写内存）**，通常无寄存器写回。
- `add`：**IF → ID（读源寄存器）→ EX（算加法）→ WB（写结果）**；在统一的五段流水中，它仍可“经过” MEM 阶段而不访问数据存储器。
- `beq`：**IF → ID（读比较操作数）→ EX（比较并判断分支）**；后续阶段是否保留、具体何时确定分支，取决于处理器设计。

### 5. 用时间表检查“周期末发生了什么”

考虑连续四条 `Load、R-type、Store、Beq` 指令：

![流水线重叠执行的周期示例](./第五章_程序的执行_配图/流水线重叠执行.png)

在**无冒险、统一五段**的示意图中：

| 时刻 | Load | R-type | Store | Beq |
| --- | --- | --- | --- | --- |
| 第 4 周期结束 | MEM | EX | ID | IF |
| 第 5 周期结束 | WB | MEM | EX | ID |
| 第 6 周期结束 | — | WB | MEM | EX |
| 第 7 周期结束 | — | — | WB* | MEM* |

`*` 表示为了画统一的五段时序图，仍保留该阶段占位；它**不意味着 `sw` 真要写寄存器，也不意味着 `beq` 必须进行数据存储器读写**。

这种时序图是学习“多条指令在同一周期分别处于哪一段”的基础，真正执行时还要考虑冒险、冲刷以及不同指令的功能差异。

## 七、流水线的冲突与冒险（Hazard）

### 1. 为什么重叠执行会出现问题

流水线通过同时处理不同指令提高吞吐率，但指令之间可能争用资源、依赖数据或者改变控制流。如果后一条指令**按原定时序继续前进会导致错误，或先前取到的指令根本不应执行**，就产生了**流水线冒险（Hazard）**。

三类冒险必须掌握：

| 类型 | 英文 | 关键原因 | 常见应对 |
| --- | --- | --- | --- |
| **结构冒险** | Structural Hazard | 同一时刻多条指令争用无法同时服务的硬件资源 | 复制资源、分离指令/数据存储资源、暂停 |
| **数据冒险** | Data Hazard | 后续指令需要的数据还没准备好 | 转发、停顿、重排指令 |
| **控制冒险** | Control Hazard | 后继指令的地址尚未确定，可能取错指令 | 分支预测、冲刷、延迟槽等 |

> [!tip] 一句话辨别冒险
> - **结构冒险：设备不够用。**
> - **数据冒险：所需数据没出来。**
> - **控制冒险：还不知道下一条该去哪。**

### 2. 结构冒险：多个指令争用同一资源

假设只有一个**单端口存储器**：当前指令在 MEM 段要读取数据，而另一条指令同时在 IF 段要从同一个存储器取指，则两个操作不能在同一个周期同时完成。

**解决办法**包括：

- 将指令存储资源和数据存储资源分开（例如教学模型中的 IM/DM 分离）。
- 增加端口或功能单元，在硬件上允许并行访问。
- 若资源冲突不可消除，则让部分指令**暂停（Stall）**。

> [!note] 与冯·诺依曼结构的联系
> 经典共享存储结构中，指令和数据可以共享存储资源；当取指和读写数据同时要求同一不可并发资源时，就形成结构冒险。采用分离的指令/数据缓存可以降低这类冲突，但实际系统仍可能在更深的存储层级发生资源争用。

### 3. 数据冒险：后面的指令依赖前面的结果

假设：

```asm
add $8, $2, $3     # 先计算$2+$3，结果准备写入$8
sub $9, $8, $4     # 紧接着读取$8，计算$8-$4
```

第二条指令读取 `$8`，但第一条指令的结果可能尚未写回寄存器组。这叫作**先写后读相关（RAW，Read After Write）**，属于最常见的数据冒险。

以无旁路的五段流水线为例：

| 指令 | 周期1 | 周期2 | 周期3 | 周期4 | 周期5 | 周期6 |
| --- | --- | --- | --- | --- | --- | --- |
| `add` | IF | ID | EX | MEM | WB | |
| `sub` | | IF | ID（想读 `$8`） | EX | MEM | WB |

在第 3 周期，`sub` 处于 ID，但 `add` 的结果还没有按照常规时序写回；如果直接读寄存器组里的旧 `$8`，就会得到错误结果。

实际中还可区分三类名称：

- **RAW（写后读依赖）**：后面要读前面写入的结果，是典型真数据依赖。
- **WAR（读后写相关）**：后面的写入可能先于前面的读取，是名称相关；在某些乱序执行结构中需要处理。
- **WAW（写后写相关）**：对同一目的位置的多次写入可能乱序完成，也是名称相关。

> [!important] 本章默认关注哪类？
> 课件五段**顺序发射、顺序执行**的入门模型主要讨论 RAW 冒险；WAR、WAW 通常不会像更复杂的乱序处理器那样成为同类流水级冲突，但学习动态调度时应知道它们的存在。

### 4. 解决数据冒险之一：转发（Forwarding）

**转发（Forwarding，又称 Bypassing，旁路）**是指：当产生结果的指令尚未完成寄存器写回时，直接将结果从后一级流水段送到需要它的执行单元输入端。

例如前述 `add` 在 EX 结束时已经得到计算结果；紧随其后的 `sub` 在下一个周期进入 EX 时，可以从流水寄存器中**旁路取得新值**，而不必等 `add` 走到 WB。

**成立条件**：所需数据必须已经由较早的流水段产生，并能在后续指令需要时及时送到对应位置。

> [!warning] 转发不是“让结果提前产生”
> 转发只减少**已经产生的结果**在传递和写回过程中的等待；如果上一条指令在需要使用时还没有算出或读取到结果，旁路仍然无能为力。

### 5. Load-use 冒险：为什么通常要停一个周期

观察两个连续的 MIPS 指令：

```asm
lw  $8, 0($2)      # 从内存取数据，直到MEM阶段末才获得加载值
add $9, $8, $3    # 下一条马上在EX阶段使用$8
```

在典型五段流水线里：

- 第 1 条 `lw`：第 3 周期计算地址（EX），第 4 周期访问内存（MEM），数据在 MEM 之后才可用。
- 第 2 条 `add`：若不暂停，第 4 周期就进入 EX，需要使用 `$8`。
- **第 4 周期 `add` 需要值的时间早于 `lw` 数据可用的时间**，单纯转发无法满足。

因此，基本五段模型通常需要**插入一个气泡（Bubble）/ 停顿一个周期**，让 `add` 的 EX 推迟到下个周期，再使用 `lw` 读取的数据。

理想示意（`—` 为尚未执行或已完成，`停` 为该指令保持在等待状态）：

| 指令 | 周期1 | 周期2 | 周期3 | 周期4 | 周期5 | 周期6 | 周期7 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `lw` | IF | ID | EX | MEM | WB | — | — |
| `add` | — | IF | ID | 停 | EX | MEM | WB |

这是一种**有冒险检测和转发支持**的典型五段时序，具体硬件实现的冻结、气泡放置方式可能略有不同。

![数据冒险及控制冒险时序](./第五章_程序的执行_配图/数据与控制冒险.png)

> [!important] 重要结论
> **相邻 `lw` 与使用其结果的指令形成的 Load-use 冒险，在课件的经典五段模型下通常需要阻塞一个周期。**
>
> 若在两者之间插入一条真正与它们无关、且能够安全移动的指令，则常可把原本浪费的停顿时间变成有效工作。

### 6. 解决数据冒险之二：寄存器组先写后读

如果某条指令在 WB 阶段写寄存器，另一条指令在同周期 ID 阶段读取**同一寄存器**，可采用适当的寄存器组时序：

**前半周期写入，后半周期读取**。

这样，同周期读取能得到新值，不必额外等待下一周期。

> [!warning] 课件时序文字的纠正
> 课件有一处描述为“前半周期读、后半周期写”。若目标是让**同一周期的后继指令读到当前周期写回的新值**，应当是**先写后读**：前半周期写，后半周期读。这里依据时序因果关系予以纠正，而非机械照抄。

### 7. 解决数据冒险之三：编译器调整指令顺序

课件使用如下彼此独立的两条高级语言语句：

```c
int a = b + c;   // 计算第一个表达式（假定b、c已定义）
int d = e - f;   // 计算第二个表达式（假定e、f已定义）
```

假设 `a,b,c,d,e,f` 都需要从内存读取或存入。以下汇编把它们映射到某个**由 `$16` 作为基址、字节偏移 0～20 的 6 个整型内存单元**，这是为便于理解而建立的示例，不依赖抽象数据类型：

**未调度（两组运算各自紧挨着执行）**：

```asm
lw  $2, 4($16)     # 从内存加载b
lw  $3, 8($16)     # 从内存加载c
add $1, $2, $3    # 立刻使用刚加载的c，可能触发load-use阻塞
sw  $1, 0($16)     # 将结果保存到a
lw  $5, 16($16)    # 从内存加载e
lw  $6, 20($16)    # 从内存加载f
sub $4, $5, $6    # 立刻使用刚加载的f，也可能触发load-use阻塞
sw  $4, 12($16)    # 将结果保存到d
```

**调度后（把独立的取数指令插到等待间隙）**：

```asm
lw  $2, 4($16)     # 先加载b
lw  $3, 8($16)     # 加载c
lw  $5, 16($16)    # 趁c的加载结果尚未就绪，先取独立的e
add $1, $2, $3    # 与加载c拉开一条指令的距离
lw  $6, 20($16)    # 再加载f
sw  $1, 0($16)     # 趁f尚未准备好，将a写回内存
sub $4, $5, $6    # 使用e、f计算e-f
sw  $4, 12($16)    # 将结果存入d
```

> [!note] 这段优化为什么成立？
> - `a=b+c` 与 `d=e-f` 在例中相互独立；移动第二组的 `lw` 不改变第一组的结果。
> - 原来的两处**紧邻 Load-use**依赖被独立指令隔开。
> - **数据依赖不能凭空消失**：若计算顺序涉及相同变量、可能存在内存别名或特殊外部副作用，编译器必须先证明重排安全。
> - 示例按课程经典五段模型说明指令调度，不代表任意 CPU 都必然获得同等周期收益。

如果找不到可安全填充的独立指令，编译器可以根据目标体系结构插入**空操作指令 NOP**（或者交由支持自动停顿的硬件处理）。

### 8. 指令调度的实际效果

课件引用了一组“访存加载导致流水线阻塞的百分比”的统计：

| 程序 | 未调度 | 经过调度 | 下降百分点 |
| --- | ---: | ---: | ---: |
| gcc | 54% | 31% | 23 |
| spice | 42% | 14% | 28 |
| tex | 65% | 25% | 40 |

由这些示例可见，编译器调度后阻塞比例明显下降；**这些数字是特定实验条件下的历史数据，并非编译优化对所有程序的必然效果**。

### 9. 控制冒险：分支为何会浪费时间

假设存在如下条件跳转：

```asm
beq $8, $9, target   # 若$8与$9相等，则跳到target标号
add $10, $2, $3     # 若分支被采用，这条顺序取到的指令可能不该执行
sub $11, $4, $5     # 同上，可能已经进入流水线
```

CPU 取到 `beq` 时，下一条正确地址还不一定确定。如果先按顺序取了 `add`、`sub`，后来判断应跳转到 `target`，这些错误路径上的指令就需要被**冲刷（Flush）**，即取消其对体系结构可见状态的影响。

控制冒险的后果：

- **停顿取指**：等目标地址确定再继续，牺牲吞吐率。
- **预测取指**：提前选择可能的执行路径，猜对时节省时间。
- **预测失败冲刷**：将错误路径的指令丢弃，重新取正确地址的指令。

> [!warning] 冲刷损失的周期数不是固定值
> 课件中的特定分支时序图给出了**冲刷三条已在流水线中的指令、损失三个时间片**的示例。实际损失与**分支在哪一级被确定、预测机制、流水线深度、取指和提交规则**等有关，并非所有五段流水线遇到分支都罚 3 周期。

### 10. 静态和动态分支预测

- **静态预测**：采用事先约定或编译期信息，如简单地预测“分支不发生”。
- **动态预测**：利用运行时历史信息估计分支是否发生、目标地址是什么。

预测的目的不是改变程序含义，而是在分支结果尚未明确时减少等待；错误预测的临时执行结果必须被适当撤销。

### 11. 分支延迟槽（Branch Delay Slot）

某些传统指令集规定，分支指令后面的一个或若干指令位置属于**分支延迟槽**：不论分支判断如何，延迟槽中的指令都会按约定执行（具体细节依 ISA 而定）。编译器可以把**不影响分支正确性、在两条路径上都安全**的指令搬进延迟槽，利用原本空闲的周期。

![分支延迟槽的调度示例](./第五章_程序的执行_配图/分支延迟槽调度.png)

下面给出一个**单延迟槽**的教学示例，使用有延迟槽语义的传统 MIPS 模型：

```asm
lw  $3, 0($2)       # 取出待比较的值
add $6, $4, $2      # 与下面的分支判断无数据依赖
beq $3, $5, target # 判断是否跳转到target
add $7, $8, $9      # 分支延迟槽：两种分支结果下均安全执行
```

- `add $7,$8,$9` 是独立且无条件都应该执行的操作，因此可以安排在延迟槽。
- **延迟槽不是“条件转移后才执行”的普通语句位置**；如果该指令只应在不跳转时执行，就不能不加分析地搬入延迟槽。
- 把原先的指令移入延迟槽后，还要确保不会引入新的数据冒险，例如把 `lw` 移到紧靠依赖它的 `beq` 之前可能产生 **Load-use 问题**。
- **现代很多处理器并不采用对软件可见的分支延迟槽**，它是理解传统流水线优化的重要历史技术。

> [!important] 三种典型解决思路对照
> - 结构冒险：**增设资源 / 避免争用**。
> - 数据冒险：**转发 / 停顿 / 静态调度**。
> - 控制冒险：**预测 / 冲刷 / 分支延迟槽（适用于特定 ISA）**。

## 八、提高性能：指令级并行与高级流水线

### 1. 什么是指令级并行（ILP）

**指令级并行（Instruction-Level Parallelism，ILP）**是指在单个指令流内部，挖掘不同指令之间可以重叠或并行执行的机会。

两种主要方向：

1. **超流水线（Super-pipelining）**：进一步细分流水段，尝试缩短时钟周期。
2. **多发射流水线（Multiple-issue Pipelining）**：同一周期启动多条指令，通过多个执行部件并行处理。

它们可以结合使用；不应把“流水段更多”和“每周期发射更多条”混为一谈。

### 2. 超流水线：进一步细分流水段

在普通单发射流水线上，一条指令可依次通过 IF、ID、EX、MEM、WB。若将原来较长的阶段进一步拆分，使每个阶段的组合逻辑延迟变短，理论上就可以提高时钟频率。

例如，某阶段组合逻辑需要 200 ps，若能近似均衡地拆为两个 100 ps 子阶段，则可能允许更短的时钟周期；**但新增的流水段寄存器会产生额外开销**。

优点：

- 更高的时钟频率。
- 在理想情况下，提高单位时间的指令完成数量。

局限：

- 流水段寄存器数量增多，开销增加。
- 数据相关与分支失败可能带来更多停顿或更高冲刷代价。
- 时序、功耗、布局、验证复杂性可能上升。
- **仅仅增加流水段，并不能让单发射处理器稳定做到每周期完成多条指令。**

> [!warning] “更多流水段”和“更大的 IPC”不等价
> 对于理想的**单发射**流水线，稳态每周期最多完成一条指令，IPC 仍然约为 1。超流水线的主要收益来自**时钟周期变短**；多发射才是在同一个时钟周期内并行启动多条指令，使理想 IPC 可以大于 1。

### 3. 多发射流水线：每周期发射多条指令

**多发射（Multiple Issue）**要求同一时钟周期能够把多条可并行执行的指令送往相应执行部件。可能需要：

- 多个整数或浮点运算部件；
- 足够的寄存器读写带宽、取指与译码带宽；
- 多个装入/存储资源；
- 对数据依赖和资源冲突进行检测、限制或调度。

例如理想的四路多发射机器：

$$\mathrm{IPC}_{\max}=4,\qquad \mathrm{CPI}_{\min}=\frac{1}{4}=0.25$$

这只是**理论上限**。实际程序的指令相关、分支、缓存和硬件资源会使平均 IPC 小于峰值。

### 4. 静态多发射：VLIW

**静态多发射**主要由**编译器在编译期**分析指令依赖、选择可以并行发射的指令，并按硬件要求组成一个**发射包（Issue Packet）**。

这种思想常与 **VLIW（Very Long Instruction Word，超长指令字）**相联系：从体系结构上将多个并行操作组织在同一个长指令或包中。课件提到 IA-64/Itanium 的 **EPIC（Explicitly Parallel Instruction Computing）**，属于显式利用指令级并行的相关设计实践。

**工作流程**：

1. 编译器识别各条指令的数据依赖和控制依赖。
2. 根据目标机器可用执行部件进行静态安排。
3. 将可并行的操作组合进同一发射包。
4. 处理指令间的冒险，并在无法填满的槽位安排空闲操作或其他合法编码。

> [!example] 为什么同一发射包中的指令有类型限制？
> 假设每周期只有**一个 ALU 运算槽**和**一个 Load/Store 槽**，那么一个发射包可以包含一条整数运算和一条访存指令，但通常不能无条件同时放两条争用同一个 ALU 槽的运算指令。
>
> 即使类型匹配，两条指令也必须满足目标机器对**数据依赖和执行时序**的约束。

优点是硬件发射决策的一部分在编译期完成；但编译结果可能和目标机器的发射宽度、功能部件布局密切相关，跨微体系结构移植及性能保持较为困难。

### 5. 动态多发射：超标量

**超标量（Superscalar）**处理器通常由硬件在运行时从常规指令流中挑选多条适合并行发射的指令。

与静态多发射相比：

| 对比 | 静态多发射（VLIW） | 动态多发射（超标量） |
| --- | --- | --- |
| 并行分组由谁决定 | 主要是编译器 | 主要是硬件 |
| 编译输出形态 | 可包含显式发射包 | 通常是正常的顺序指令流 |
| 依赖分析的时机 | 侧重编译时 | 运行时进行必要检测 |
| 对硬件结构的适配 | 编译代码往往较依赖目标发射结构 | 硬件根据本机资源动态决定发射 |
| 主要成本 | 编译、调度及体系结构约束 | 复杂发射、调度和相关性检测硬件 |

> [!important] 超标量 ≠ 必然乱序
> **超标量**强调每周期可以发射多条指令；**乱序执行**强调在保证程序可见结果正确的前提下，允许指令在内部不完全按原始顺序执行。现代高性能处理器常将两者结合，但它们是两个不同的概念。

### 6. 动态流水线调度与乱序执行

**动态流水线调度（Dynamic Pipeline Scheduling）**让处理器在发现前面的指令因数据未就绪而等待时，寻找后面**不依赖这个未就绪数据**的指令先执行，以减少功能部件空闲。

课件使用的例子可用以下 MIPS 风格指令说明：

```asm
lw   $8, 20($2)     # 从内存加载数据到$8，可能需要等待MEM结果
addu $9, $8, $10    # 依赖上一条lw的结果，暂时不能执行
sub  $12, $12, $11  # 与lw和addu没有数据依赖，可先执行
slti $13, $12, 20   # 依赖sub写入的$12，必须等待sub产出结果
```

关键依赖关系：

- `lw → addu`：`addu` 必须等待 `$8` 可用。
- `sub → slti`：`slti` 必须等待更新后的 `$12`。
- `sub` **不依赖** `lw`，因此有可能在 `addu` 等待时先执行。

![动态多发射与调度示例](./第五章_程序的执行_配图/动态多发射与乱序.png)

> [!note] 乱序执行必须保证什么？
> 乱序强调**内部实际执行顺序**可调整，不代表程序最终表现可任意变化。现代乱序处理器通常通过相关性检测、寄存器重命名及按序提交等机制，使程序看到的结果仍符合体系结构所承诺的执行语义；这里只需理解其基本动机，不要求掌握完整硬件实现。

### 7. 三种提高并行度的方式速查

| 技术 | 最主要改变 | 理想效果 | 突出问题 |
| --- | --- | --- | --- |
| **超流水线** | 增加流水段，缩短周期 | 时钟频率可提高 | 流水段寄存器与冒险代价增加 |
| **静态多发射 / VLIW** | 编译期决定多条指令同时发射 | 理想 IPC 可大于 1 | 编译器依赖目标机器结构，打包受限 |
| **动态多发射 / 超标量** | 硬件运行时决定发射组合 | 利用实际运行的 ILP | 调度和依赖检测硬件复杂 |

## 九、章节知识联系与易错点

### 1. 指令周期、机器周期、时钟周期的区别

- **指令周期**：执行一条指令所经历的总体过程或时间。
- **机器周期**：传统模型中用于划分 CPU 主要操作的中间时间单位；不同教材和机器结构的使用方式可能不同。
- **时钟周期**：同步时钟的一个周期，由硬件时钟频率决定。

课件最后强调，现代流水线处理器通常直接用时钟周期分析执行过程，**不再适宜把传统机器周期模型套用于所有现代 CPU**。

**流水线中的单条指令跨越多个时钟周期**，但稳定工作时**多个不同指令可以在一个时钟周期内同时推进**。这并不矛盾。

### 2. CPU 总线式数据通路与流水线式数据通路

课件提到早期 CPU 内部常以总线连接寄存器、ALU、暂存器和 IR 等，可区分：

- **单总线**：多个部件共享一条内部数据总线，结构相对简单，传送调度受限。
- **双总线**：增加并行数据通道，减少部分传送竞争。
- **三总线**：可为两个源操作数及一个结果提供更灵活的传送路径，常用于说明寄存器到 ALU 的并行操作。

流水线数据通路则更加重视**按执行阶段组织组合逻辑和流水段寄存器**。内部总线数量与是否使用流水线不是绝对互斥的设计标签，可以从不同角度描述同一 CPU 的组织方式。

### 3. 典型易错点总表

| 易错说法 | 正确理解 |
| --- | --- |
| “PC 每执行一条指令都加 1” | PC 顺序增量取决于指令长度与寻址单位；分支时可能跳转 |
| “编译好的程序直接以汇编文本运行” | CPU 执行的是机器指令编码 |
| “取指、译码、执行必须严格串行且各占一周期” | 那是逻辑划分；具体实现可组合、重叠与流水化 |
| “五段流水线使单条指令延迟减为 1/5” | 主要改善吞吐率，单条指令延迟可能增加 |
| “五段流水线加速比一定是 5” | 需要段平衡、开销小、指令多且无冒险等理想条件 |
| “出现数据相关就必须等待 WB” | 已产生的结果可通过转发提前利用 |
| “所有 Load-use 冒险都能靠转发消除” | 经典五段模型中紧邻的 Load-use 仍需停顿 |
| “后半周期写就能让本周期先读取的指令得到新值” | 典型先写后读时序要求**前半周期写、后半周期读** |
| “Flush 和 Stall 是一回事” | Stall 暂停推进；Flush 取消错误路径或无效指令 |
| “RISC 永远比 CISC 快” | 两者是 ISA 设计风格，实际性能取决于整体实现 |
| “超流水线能让单发射 IPC 达到 4” | 超流水线重点是缩短周期；IPC 大于 1 通常需要多发射 |
| “乱序执行可以破坏程序结果” | 必须遵守 ISA 的可见行为与依赖要求 |

> [!warning] 课件中需特别纠正或限定的三处
> 1. **吞吐率单位换算**：`1/600ps` 应为约 $1.67\times10^9$ 条/秒（**1.67 GIPS**），而非 $1.67\times10^{12}$ 条/秒。
> 2. **同周期寄存器先写后读**：为保证读取到新值，应是**前半周期写、后半周期读**，不是反过来。
> 3. **流水线与复杂指令集的定性结论**：诸如“五级一定加速五倍”“RISC 指令总在一个周期内完成”“CISC 无法高效流水”“x86 指令长度可到 17 字节”等，都不能不加条件地推广。正确的解释分别涉及段平衡与寄存器开销、完成延迟与吞吐量区分、现代微体系结构、以及 x86 15 字节的编码上限。

## 十、典型复习题（含参考解答）

### 题 1：根据指令识别执行流

给定以下 MIPS 风格片段，`$8` 和 `$9` 的值相等时，CPU 后续应从哪里继续取指？

```asm
beq $8, $9, target  # 寄存器相等则跳到target
add $10, $2, $3     # 位于分支后的顺序地址
```

> [!example] 参考解答
> 在**不采用软件可见分支延迟槽**的抽象模型里，分支成立后下一条体系结构上应执行的指令位于 `target`；已从顺序路径预测取得的指令可能需要被冲刷。
>
> **若使用传统 MIPS 分支延迟槽语义**，`beq` 后紧邻的延迟槽指令还会按该 ISA 的规则执行，然后再转到目标位置。应先看题目规定的分支模型，不能把两种架构语义混合。

### 题 2：单周期与流水线性能比较

五段组合逻辑延时分别为 $200,50,100,200,50\;\mathrm{ps}$，寄存器开销 $50\;\mathrm{ps}$。两种方案执行 20 条连续无冒险指令，求时间及加速比。

> [!example] 参考解答
> 单周期时钟周期：$600\;\mathrm{ps}$，因此
>
> $$T_{\text{单}}=20\times600=12000\;\mathrm{ps}$$
>
> 流水线时钟周期：$200+50=250\;\mathrm{ps}$，总周期数：$20+5-1=24$，所以
>
> $$T_{\text{流水}}=24\times250=6000\;\mathrm{ps}$$
>
> $$\boxed{S=12000/6000=2}$$
>
> 注意第 20 条指令的完成时间不能简单写为 $20\times250$；还需计入启动与排空。

### 题 3：识别数据冒险

```asm
lw  $8, 0($2)     # 将内存中的数据加载到$8
sub $9, $8, $3   # 下一条马上使用$8
```

问：属于哪类冒险？在经典五段流水线、带转发的条件下是否需要停顿？

> [!example] 参考解答
> - 属于**RAW 数据冒险**，具体是 **Load-use**。
> - `lw` 的结果需要在 MEM 阶段读取，紧接着的 `sub` 在 EX 阶段就需要该值。
> - **经典五段模型中通常暂停 1 个周期**，即使具有通常的转发机制，也不能在所需时间之前获得尚未读出的数据。

### 题 4：识别结构冒险

在某一周期，第一条指令执行数据读取，另一条指令需要取下一条指令，但 CPU 只有一个不能并行使用的存储器端口。问产生什么问题？

> [!example] 参考解答
> 属于**结构冒险**：两条指令同时争用同一个端口。可通过区分取指资源与数据存储资源、采用多端口结构，或者插入停顿进行处理。

### 题 5：计算多发射处理器性能

一台处理器频率为 $2\;\mathrm{GHz}$，平均 $\mathrm{IPC}=2.5$，问平均指令吞吐率是多少？若要完成 $10^{10}$ 条指令，忽略额外影响，需要多长时间？

> [!example] 参考解答
> $$
> \text{吞吐率}=2.5\times2\times10^9=5\times10^9\;\text{条/秒}
> $$
>
> $$
> \boxed{T=\frac{10^{10}}{5\times10^9}=2\;\mathrm{s}}
> $$
>
> 对应 $\mathrm{CPI}=1/2.5=0.4$，说明机器平均每周期完成了不止一条指令。

### 题 6：解释动态调度的作用

```asm
lw   $8, 0($2)       # 内存读取，可能尚未就绪
addu $9, $8, $10     # 与lw存在RAW依赖
sub  $11, $12, $13   # 不依赖前两条指令
```

为什么在允许乱序执行的微体系结构里，`sub` 有机会早于 `addu` 执行？

> [!example] 参考解答
> `addu` 需要等 `lw` 把 `$8` 准备好，而 `sub` 使用的是 `$12`、`$13`，与尚未就绪的 `$8` 无关。只要硬件资源和其他依赖允许，处理器就可以先执行 `sub`，填补 `addu` 等待造成的空闲，但必须维护正确的体系结构可见结果。

## 十一、最终速查

> [!summary] 本章核心结论
> **程序执行**：PC 控制取指地址，CPU 经由数据通路与控制器完成取指、译码、取数、运算、结果写回；分支、异常和中断可以改变控制流。
>
> **流水线**：不同指令在不同阶段重叠执行，主要改善**吞吐率**，不保证缩短单条指令延迟。
>
> **理想 $k$ 段流水线**：$N$ 条指令共需 $N+k-1$ 个周期（不含额外停顿和冲刷）。
>
> **三种冒险**：结构冒险（争用硬件）、数据冒险（数据未就绪）、控制冒险（下一地址未确定）。
>
> **RISC 设计风格**：规整、简化、Load/Store 分离，有助于流水线；与 CISC 不存在不看实现的绝对性能优劣。
>
> **高级流水线**：超流水线缩短时钟周期；VLIW 由编译器静态安排并行；超标量由硬件动态发射；乱序执行用于隐藏部分等待延迟。

### 核心公式

| 用途 | 公式 | 主要条件 |
| --- | --- | --- |
| 程序执行时间 | $T=N\times\mathrm{CPI}\times t_{\text{clk}}$ | 使用平均 CPI |
| 指令吞吐率 | $\text{Throughput}=\mathrm{IPC}/t_{\text{clk}}$ | 匹配稳态或观测区间 |
| CPI / IPC | $\mathrm{IPC}=1/\mathrm{CPI}$ | 对相同指令计数与时间区间取平均 |
| 流水时钟周期 | $t_{\text{clk}}\approx\max(t_i)+t_{\text{reg}}$ | 典型同步分段模型 |
| 理想流水总周期数 | $C=N+k-1$ | 每段等周期、每周期启动一条、无冒险 |
| 理想流水总时间 | $T=(N+k-1)t_{\text{clk}}$ | 同上 |
| 加速比 | $S=T_{\text{旧}}/T_{\text{新}}$ | 比较同一工作量 |
| N 批衣服串行时间 | $T=90N\;\mathrm{min}$ | 每批 30+40+20 分钟 |
| N 批衣服流水时间 | $T=40N+50\;\mathrm{min}$ | 最慢烘干段为 40 分钟且连续安排 |
